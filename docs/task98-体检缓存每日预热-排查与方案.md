# #98 策略体检缓存：每日自动预热

> 诉求：体检缓存能不能每天自动缓存？
> 结论：**能，而且现在已经在跑**——但它是搭日线落库的车，有 4 个缺口。
> 本轮改成独立每日调度 + 按数据判脏。

## 1. 现状：现在到底怎么预热的

三个触发点，全部**依赖落库**：

| 触发点 | 位置 | 条件 |
|---|---|---|
| 落库成功后顺手预热 | `scheduler.py:188` | 每天 15:30 自动落库，**且当天判定为交易日、且落库成功** |
| 服务启动补跑 | `app.py:211` | `only_if_synced_today=True`——今天必须已落库成功 |
| 后台手动预热 | `app.py:2940` | 人工点按钮 |

**缺口（这就是"感觉没自动"的原因）**：

| 场景 | 现在 |
|---|---|
| 交易日 15:30 落库成功 | ✅ 自动预热 |
| 周末 / 节假日 | ❌ 判定非交易日 → 不落库 → 不预热 |
| 当天落库失败 | ❌ 不预热，缓存停在昨天 |
| 服务白天重启、今天还没落库 | ❌ 启动补跑被 `only_if_synced_today` 挡掉 |
| 手动清空缓存后 | ❌ 只能手动点，或等明天落库 |

### 实测数据（本轮量的，不是照抄注释）

| 项 | 实测 |
|---|---|
| 单次评估耗时 | **230.4 秒**（`cost_seconds`），远慢于注释里写的 90~150 秒 |
| `SELECT MAX(date) FROM daily_bars` | **0.000 秒**（走 `idx_bars_date`） |
| 当前缓存 `as_of` | 2026-09-24 |
| 当前 `daily_bars` MAX(date) | 2026-09-24（**一致，无需重算**） |
| 缓存覆盖 | 120 天 / 前向 5 / 15 个策略 |

**这两条数据决定了设计**：重算一次要满载烧 4 分钟 CPU，而判脏几乎零成本。
所以绝不能"每天无脑算一遍"，必须按数据判脏。

但**复用它的三个成熟做法**：状态存 meta 表、日期字符串比对、脏值回落默认。

## 3. 风险排查（12 项，R1/R4 已实测）

| # | 风险 | 后果 | 方案 |
|---|---|---|---|
| R1 | 单次评估实测 **230 秒**，CPU 满载 | 卡住选股/页面 | ①按数据判脏挡掉无谓重算 ②16:30 与落库 15:30 错开 1 小时 ③后台线程 + 单锁，不阻塞请求 |
| R2 | 调度线程重复启动 | 多个线程同时预热 | 模块级 `_sched_started` 标志 + daemon 线程（同 `scheduler._start`） |
| R3 | 服务重启后"今天跑过没"丢失 | 重复跑或漏跑 | 状态存 meta 表（`eval_prewarm_last_try/ok/result`），重启后照样知道 |
| R4 | 判脏要读 `daily_bars` MAX(date) | 慢？ | **实测 0.000s**（走 `idx_bars_date`），零成本，可以每分钟放心读 |
| R5 | 历史引擎 `as_of` 滞后于 DB（引擎未 reload） | 误判"数据变了"白算，或反之漏算 | 判脏基准取 **DB MAX(date)**（权威），缓存侧取 `_HITS_CACHE["as_of"]`；预热内部本来就有 `history.reload_engine()` |
| R6 | 手动清空缓存后，数据没变 → 永远不自动预热 | 缓存一直空，体检页没数据 | 判脏第一条：**缓存为空 → 必须算**（不是可选项，是正确性问题） |
| R7 | 时间配置脏值（`25:00` / `abc` / 空） | 调度永不触发 | 正则 `^([01]\d\|2[0-3]):([0-5]\d)$`，不合法回落 `16:30`（与 `scheduler._run_at` 同款） |
| R8 | "下次运行时间"跨午夜算错 | 面板显示误导 | 复用 `scheduler._next_run_text` 的估算写法，并注明"跳过周末、不管节假日" |
| R9 | 定时触发与"落库后立即触发"重复 | 同一天算两遍 230 秒 | 两条路径共用 `_PREWARM_LOCK` 与同一判据；已算过则缓存 key 相同 → 判脏为"无需重算" |
| R10 | 系统休眠 / 时钟漂移 | 漏跑 | 用**日期字符串比对**而非时间差（同 `scheduler`），睡多久都不会漏或重 |
| R11 | 新调度与 `only_if_synced_today` 冲突 | 补跑被挡 | 新调度走独立入口，**不传**该参数；落库触发保留原样 |
| R12 | meta 表写入失败（库忙） | 调度状态丢失 | 全部 try/except，失败只记日志，不影响预热本身 |


返回 `{due: bool, reason: str, db_max_date, cache_as_of}`，面板直接显示 reason。

### 4.2 每日调度（16:30，环境变量可覆盖）

- 每分钟醒一次，比对「当前 HH:MM ≥ at」且「今天还没成功跑过」
- 到点先 `prewarm_due()`，不 due 就只记一条 `last_result` 说明为什么跳过
- 状态写 meta：`eval_prewarm_last_try` / `last_ok` / `last_result`
- 环境变量 `TICK_EVAL_PREWARM_AT`，默认 `16:30`

### 4.3 暴露给界面

`cache_status()` 与 `/api/admin/eval_cache` 增加：

```json
"schedule": {"enabled": true, "at": "16:30", "next": "今天 16:30",
             "last_ok": "2026-09-28", "last_result": "...",
             "due": false, "due_reason": "数据未更新（2026-09-24），无需重算"}
```
