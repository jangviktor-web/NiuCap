# 历史行情落库说明

## 为什么需要落库

改造前，「策略选股」只依赖 **当日快照字段**（涨跌幅、换手率、成交额等），
不拉历史 K 线。看 `server/screener.py` 的注释：

> 策略基于当日快照字段（无需逐股拉K线，秒级扫全市场）

所以像「平台突破」「均线多头」这些**名字上要求历史数据**的策略，
实际实现是用当日涨跌幅近似的伪形态 —— 比如 `s_platform_break`：

```python
if 4.0 <= cp <= 9.9 and op < hi and to >= 2.0:
    out.add(r["code"])
```

判断「今天涨 4%~9.9% 且非一字板」，**完全没看前 60 日是不是横盘**。

真正需要历史数据的策略（参考 myhhub/stock 的做法）：
- **回踩年线**：前段从年线下方突破 → 后段在年线上方运行 → 回踩缩量
- **停机坪**：连续 3 天高开收涨振幅 <3%，前置条件是 15 日内有涨停
- **无大幅回撤**：60 日内不能有单日跌 7%、两日累计跌 10%

这些用当日快照**根本算不出来**。把日线沉淀到库里，是解锁这类策略的前提。

## 性能特征（实测数据）

### 数据源：两种可选，用 `--source` 切换

**eltdx（默认）** 走通达信 7709 协议，支持【一次请求批量取多只】，
彻底绕开了腾讯源的 400ms 限流：

| 范围 | 股票数 | eltdx 实测 | 腾讯源 |
|---|---|---|---|
| 单只 250 根 | 1 | **0.036 秒** | 0.40 秒 |
| 沪深300 | 300 | **37 秒**（取数 2.5s + 写入 8.7s） | 约 4 分钟 |
| 全市场 | 5575 | **取数 15.9 秒** | 约 48 分钟 |

批量取数呈完美线性（实测 10 只 0.09s / 100 只 0.87s / 300 只 2.58s）。

**额外收益**：eltdx 提供腾讯源缺失的**成交额 `amount`** 字段。腾讯源的
K 线接口此字段恒为 `None`，导致改造前库里 `daily_bars.amount` **全部为 NULL**
（实测 1500/1500 行）。接入 eltdx 后覆盖率 100%。

> ⚠️ **必须显式传 `adjust='qfq'`**。eltdx 的 `adjust` 默认是 `None`（不复权），
> 会让除权股静默产生约 1.8% 的偏差（实测 `sh601318` 有 28 处不符）。
> 前复权后与腾讯源偏差 0.000%。适配器已内置该默认值。

> ⚠️ **成交量取 `volume_lots`（手），不是 `volume_wire_value`（股）**。
> 实测 `腾讯.volume / volume_lots = 1.0000`，口径完全一致；
> `volume_wire_value` 差 100 倍，混用会导致成交量放大百倍。

### 停牌占位行的处理

通达信对停牌日会返回一条 **OHLC 四价全等、且 `volume=0`** 的占位记录
（实测沪深300 中 `sh601059`/`sh601238`/`sh601995` 在 2026-09-21 就是这种行）。

这类行**必须剔除**，否则会污染指标计算 —— 把 `volume=0` 算进「均量」
会低估基准，让后续「放量」判断失真。适配器默认过滤（`DROP_SUSPENDED`），
并叠加「四价全等」特征避免误杀正常零成交场景。

剔除后 `sh601059` 的最新日期从 `2026-09-21` 归位到真实的 `2026-09-14`，
这正是 `策略改造难点评估.md` 里标的**难点 2 · 停牌 / 数据滞后**的处理方案。

### 写入侧：TiDB 的网络往返

TiDB Cloud Serverless 单次往返约 **190~260ms**，所以写入成本几乎
完全由【语句条数】决定，与数据量基本无关：

| 写入方式 | 500 条耗时 | 每条 |
|---|---|---|
| 逐行 INSERT + 逐行 commit | ~3 分钟 | 367 ms |
| 逐行 INSERT（仅末尾 commit） | ~90 秒 | 181 ms |
| **多值批量 INSERT（100 行/语句）** | **~1.4 秒** | **2.8 ms** |
| 单条 SQL 灌 200 行 | ~1 秒 | 1.9 ms |

> 关键改动：`upsert_bars` 用多值 INSERT 把 N 行合成一条 SQL。
> **这条优化让写入快了约 130 倍，切勿改回逐行。**

### 连接探活（`_conn()` 的 ping）

`_conn()` 原本每次取用都 `ping()` 一次验证连接存活，而 TiDB 上
**ping 本身就是一次约 200ms 的往返**。一次落库流程会调用 `_conn()`
多次（`upsert_bars`、`record_sync` 各一次），凭空吃掉近 1 秒/只。

修复：给 ping 加 **30 秒节流窗口**（`_conn()` 内 `_PING_IDLE`），
窗口内复用连接不再探活。可用环境变量 `TICK_DB_PING_IDLE` 调整，
设为 `0` 则回到旧行为（每次必 ping）。

### 腾讯源侧：`_throttle` 是速率上限，不是锁竞争

`_throttle("tencent_kline", 0.4)` 固定 400ms/请求。实测数据源拉取
约 **0.36s/只，其中几乎全是这 400ms 的等待**，真实网络请求不到 60ms。

> 注意：这是**速率上限**而非锁竞争 —— 并发请求同一域名会被限速，
> 所以加线程**突破不了**（实测 1/4/8 并发均为 0.36~0.40s/只）。
> 这也正是 eltdx 批量取数能把全市场从 48 分钟压到 16 秒的原因。

顺带修正了 `_throttle` 的实现：旧写法「持锁 sleep」会让所有线程串行
等待；现改为「锁内预留时间片 + 锁外 sleep」，限流语义不变但等待可并行。

### 当前端到端表现

**eltdx 源（默认）**：

| 范围 | 股票数 | 实测耗时 |
|---|---|---|
| 沪深300 | 300 | **约 0.6 分钟**（取数 2.5s + 写入 8.7s） |
| 全市场 | 5565 | **3.3 分钟**（取数 37.8s + 写入 159.2s，SQLite 后端） |

全市场实测明细（`--scope all --count 500 --workers 8`）：

```

取到 5565/5575 只，耗时 37.8s（6.8 ms/只）
已剔除 12 条停牌占位行
⚠ 10 只无数据（已发行未上市的新股，代码表先行收录）
写入完成，耗时 159.2s（28.6 ms/只）
────────────────────────────────
同步完成：成功 5565 只，共写入 2,707,426 条，耗时 3.3 分钟
```

**腾讯源（`--source tencent`）**：

| 范围 | 股票数 | 实测/预计耗时 |
|---|---|---|
| 单只 | 1 | 约 0.76 秒 |
| 沪深300 | 300 | 约 4 分钟 |
| 中证500 | 500 | 约 6 分钟 |
| 全市场 | 3761 | 约 48 分钟 |

用 eltdx 后，**瓶颈已从「数据源限流」回到「数据库写入」**
（全市场写入 159s vs 取数 38s）。本地 SQLite 后端写入已属较快，
换 TiDB Serverless 会明显更慢（单次往返 190~260ms）。

## 使用方法

### 同步数据

```bash
# 沪深300（推荐日常使用，eltdx 源约 37 秒）
python3 scripts/sync_bars.py --scope hs300

# 全市场（建议收盘后跑）
python3 scripts/sync_bars.py --scope all

# 指定股票
python3 scripts/sync_bars.py --codes sh600519,sz000001

# 拉更多历史（800 根 ≈ 3.2 年）
python3 scripts/sync_bars.py --scope hs300 --count 800

# 强制走腾讯源（不使用 eltdx）
python3 scripts/sync_bars.py --scope hs300 --source tencent

# 并发数（eltdx 源下只影响落库阶段；腾讯源下超过 4 无提升）
python3 scripts/sync_bars.py --scope hs300 --workers 6
```

### 数据源选择

| `--source` | 说明 |
|---|---|
| `auto`（默认） | 优先 eltdx，不可用时自动降级腾讯源 |
| `eltdx` | 强制 eltdx，不可用则报错退出 |
| `tencent` | 强制走原腾讯源（兼容旧行为） |

环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `TICK_ELTDX` | `1` | 设 `0` 可**全局关闭** eltdx，一键退回腾讯源 |
| `TICK_ELTDX_SERVERS` | `4` | 通达信服务器数 |
| `TICK_ELTDX_CONNS` | `6` | 每台服务器的 TCP 连接数 |
| `TICK_ELTDX_KEEP_SUSPENDED` | `0` | 设 `1` 保留停牌占位行（默认剔除） |

### 查看状态与自检

```bash
python3 scripts/sync_bars.py --status          # 落库覆盖情况
python3 scripts/sync_bars.py --check-source    # 数据源自检（连通/单位/正确性）
python3 scripts/sync_bars.py --scope hs300 --dry-run   # 只统计不发请求
```

> `--check-source` 会校验三个最容易出错的点：**volume 单位是否为「手」**、
> **amount 单位是否为「元」**、**amount 是否约等于 close×volume×100**。
> 换数据源前务必先跑一次 —— 单位错了不会报错，只会静默落库错误数据。

### scope 取值

| scope | 含义 | 股票数 | pools 代码 |
|---|---|---|---|
| `all` | **全市场**（eltdx 完整代码表，含北交所） | 5575 | — |
| `snapshot` | 旧快照口径（新浪分页，无北交所） | 3761 | — |
| `hs300` | 沪深300 | 300 | 000300 |
| `zz500` | 中证500 | 500 | 000905 |
| `zz1000` | 中证1000 | 1000 | 000852 |
| `zz2000` | 中证2000 | — | 932000 |

也可直接传指数代码，如 `--scope 000300`。

> **`all` 与 `snapshot` 的区别很重要**：实测 `snapshot` 的 3761 只是 `all`
> 的 5575 只的**严格子集**（交集 3761、「仅池中有」0 只）。新浪分页有抓取
> 上限且**完全不含北交所（349 只）**。要把覆盖率拉满必须用 `all`。

## 数据结构

### daily_bars（日线表）

| 字段 | 类型 | 说明 |
|---|---|---|
| code | TEXT/VARCHAR(32) | 股票代码，如 `sh600519` |
| date | TEXT/VARCHAR(16) | 交易日 `YYYY-MM-DD` |
| open/close/high/low | REAL/DOUBLE | OHLC |
| volume | REAL/DOUBLE | 成交量（**单位：手**） |
| amount | REAL/DOUBLE | 成交额（**单位：元**）。eltdx 源才有值 |
| updated_at | REAL/DOUBLE | 入库时间戳 |

**主键是 `(code, date)` 而非自增 id** —— 保证重复同步同一段不产生重复行（幂等）。

> `amount` 在改造前恒为 NULL（腾讯源不提供），接入 eltdx 后覆盖率 100%。
> 落库前请确认单位：`volume` 是手、`amount` 是元，可用 `--check-source` 校验。

### bar_sync（同步进度表）

记录每只股票已同步到哪一天、共多少条、是否出错，支持断点续查。

| 字段 | 说明 |
|---|---|
| code | 股票代码 |
| last_date | 已同步到的最新交易日 |
| bars | 已入库条数 |
| synced_at | 本次同步时间戳 |
| status | `ok` / `empty` / `error` |
| err | 出错信息（截断 500 字符） |

## 接口

| 接口 | 说明 |
|---|---|
| `GET /api/bars/status` | 落库覆盖情况 + 最近同步记录 |
| `GET /api/bars/{code}` | 从本地库读某只股票的历史日线（不请求外部源） |

`/api/bars/{code}` 支持 `end` 参数做历史时点回看（只取该日期之前的数据），
便于将来做「过去某一天如果按此策略选股会怎样」的回溯测试。

## 代码位置

| 文件 | 作用 |
|---|---|
| `server/store.py` | `upsert_bars` / `get_bars` / `bars_coverage` / `record_sync` / `sync_status` |
| `scripts/sync_bars.py` | 同步脚本（含数据源选择与自检） |
| `server/sources/eltdx_source.py` | eltdx 适配器 —— 全工程**唯一** `import eltdx` 的地方 |
| `server/sources/__init__.py` | 数据源总开关 `TICK_ELTDX` |
| `server/app.py` | `/api/bars/status`、`/api/bars/{code}` |

数据库 DDL 同时支持 SQLite 与 TiDB，见 `store.py` 的 `_SCHEMA_SQLITE` / `_SCHEMA_MYSQL`。

### 为什么把 eltdx 单独隔离成一个适配器

eltdx 的许可证（ELTDX Research-Only License）**明确禁止商业使用**，
且走通达信非公开协议、无 SLA。集中在一个文件里的好处：

1. 将来若要摘除（例如面板转为对外服务），删文件 + 改开关即可，调用不散落各处
2. 可做优雅降级：eltdx 不可用时自动回落腾讯源，业务无感
3. 复权口径、单位换算、停牌过滤这些易错细节集中处理

详见 `docs/eltdx引入评估.md`。
