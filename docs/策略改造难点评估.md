# screener.py 策略改造 · 难点评估报告

> 目标：把 `screener.py` 里 6 个「伪历史策略」改成基于 `daily_bars` 的真实计算。
>
> **状态：改造已完成并验证通过。**
> 6 个难点全部关闭（难点 1/2 由 eltdx 全市场落库解决，3/4/5/6 由 `history.py` 解决），
> 6 个策略与 pandas 独立复算**零分歧**，端到端 API 已验证。
> 改造过程与准确性证据见 [`策略改造报告.md`](./策略改造报告.md)。

## 一、改造范围：6 个策略

`screener.py` 共 15 个策略，按「策略语义是否要求历史数据」分类：

### 需要改造（伪历史）— 6 个

| 策略 | 名称 | 名字承诺 | 当前实现 | 差距 |
|---|---|---|---|---|
| `s_breakout_20h` | 突破新高 | 突破 20 日新高 | `high >= prev*1.095` 且涨幅>5% | **只看今日一根**，与「20日新高」无关 |
| `s_ma_bull` | 均线多头 | MA 多头排列 | 涨幅 2%~8% + 换手 1%~15% | **完全没算均线** |
| `s_platform_break` | 平台突破 | 横盘后突破 | 涨幅 4%~9.9% + 非一字板 | **没看前 60 日是否横盘** |
| `s_volume_surge` | 放量突破 | 放量 | 成交额>3亿 且涨幅>3% | 绝对额门槛，**非相对自身均量** |
| `s_oversold_rebound` | 超跌反弹 | 超跌 | 涨 1%~6% + 换手 4% | **没看前期跌幅** |
| `s_pullback_ma20` | 回踩企稳 | 回踩 MA20 | 涨跌 -2%~+2% + 换手 | **没算 MA20，也没判断回踩** |

> 前 4 个的名字直接写着 `20h` / `ma` / `platform` / `volume`，语义与实现脱节最明显。

### 无需改造 — 9 个

`s_gap_up`、`s_limit_up`、`s_near_limit`、`s_limit_up_momentum`、`s_strong_turnover`、
`s_vol_price_up`、`s_reversal_hammer`、`s_low_vol_leader`、`s_small_cap_active`

这些语义本身就是**当日截面**（涨停、换手、下影线都是当日 K 线内信息），
不依赖历史，保持现状即可。

## 二、6 个难点，逐个实测

### 难点 1 · 覆盖率只有 8.1% ⚠️ 需决策

```
全市场快照    : 3761 只
已落库日线    :  306 只   ← 覆盖率 8.1%
有快照无日线  : 3455 只
有日线无快照  :    0 只
```

改造后的策略**只能对已有日线的股票计算**。两条路：

| 方案 | 说明 | 代价 |
|---|---|---|
| A. 先全量落库 | 跑一次 `--scope all`（3761 只，约 48 分钟） | 一次性的 48 分钟 |
| B. 渐进生效 | 策略只返回有数据的，覆盖率随日常同步自然提升 | 初期结果偏少 |

**建议 A**。理由：策略结果「只覆盖 8% 股票」会让用户误判（以为全市场就这几只满足），
不如先把数据补齐。48 分钟一次性成本可以接受。

---

### 难点 2 · 数据新鲜度 / 停牌 ⚠️ 必须处理

实测发现**日线最新日期并非全部对齐到当天**：

| 代码 | 日线最新日期 | 根数 | 判断 |
|---|---|---|---|
| `sh601238` | 2026-09-11 | 500 | 停牌 |
| `sh601995` | 2026-09-14 | 500 | 停牌 |
| `sh601059` | 2026-09-14 | 500 | 停牌 |
| 其余 303 只 | 2026-09-21 | 501 | 正常 |

**风险**：如果直接用「数组最后一个元素」算 MA，停牌股会被当成**当前有信号**，
但它其实已经十几天没交易了 —— 这是**逻辑错误**，不是精度问题。

**处理**：每个策略计算前校验 `最新日期 == 快照交易日`，不一致直接跳过该股票。
盘中运行时快照是实时价、日线是昨收，需要放宽一天，这个边界要明确定义。

---

### 难点 3 · 读取性能 🔴 最大的坑，已找到解法

最初设想是「按需查库」（每个策略要哪只就读哪只），**实测完全不可行**：

| 读取方式 | 实测 | 全市场推算 |
|---|---|---|
| 逐只 `get_bars(code, limit=60)` | 278 ms/只 | **17.4 分钟** ❌ |
| 单次 SQL `WHERE code IN (50只)` | 6.85 s | 更慢 ❌ |
| **一次读全表 ORDER BY code,date** | **1.14 ~ 3.7 s** | **可行** ✅ |

**关键结论**：成本由 **RTT（~200ms）** 决定，与行数关系极小。
读 1 万行 1.27s、读 15 万行 1.14s —— 数据量翻 15 倍，耗时反而略降。

> 推断：TiDB Serverless 的往返延迟是固定开销，一旦开始流式返回，
> 行数对总耗时的影响远小于网络握手。

**所以必须「全表一次性加载 + 内存分组」，绝不能逐只查库。**

---

### 难点 4 · 内存占用 ⚠️ 已找到解法

朴素方案（`dict[code] -> list[dict]`）内存不可接受：

| 存储方式 | 15 万行 | 188 万行推算 |
|---|---|---|
| `list[dict]` | 41 ~ 503 MB | **503 MB+** ❌ |
| **numpy float32 数组** | **2.9 ~ 4 MB** | **36 ~ 50 MB** ✅ |

**省约 10 倍**。转换成本仅 0.09~0.31 秒，几乎免费。

结构设计：
```python
# code -> {'open': np.ndarray, 'high': ..., 'low': ..., 'close': ..., 'volume': ...}
# 另存 code -> np.ndarray(dtype='U10') 的日期数组（或单独 dict 存最新日期）
```

---

### 难点 5 · 全量加载耗时 🔴 需要缓存

```
SQL 读取          : 2.76 s   ← RTT 主导，基本恒定
分组 + numpy 化   : 0.31 s   ← O(n)，随数据量线性增长
合计              : 3.07 s   (306 只 / 15.3 万行)
→ 188 万行推算    : 约 37.9 s  ❌ 不能每次选股都做
```

**处理：进程内缓存 + 按天失效。**

- 日线一天只更新一次（收盘后同步），TTL 设 1 天完全够
- 首次访问付出 ~38 秒，之后**全部命中缓存**
- 需要提供手动失效入口（同步完成后刷新），否则当天新同步的数据看不到

> 也可以考虑缓存到磁盘（pickle / .npy），冷启动从 38s 降到几秒。
> 但会引入「缓存文件与实际库不一致」的新问题，**建议先做纯内存版**，
> 简单可靠，毕竟一天只冷启动一次。

---

### 难点 6 · 指标计算性能 ✅ 完全不是问题

这是唯一一个**比预想好得多**的环节：

| 计算内容 | 306 只 | 3761 只推算 |
|---|---|---|
| MA5/10/20/60 多头判断 | 4.3 ms | **53 ms** |
| 全套指标（6 条均线 + 20日高低 + 5/20日均量 + 涨跌幅） | 9.0 ms | **110 ms** |

numpy 向量化后，**全市场算全套指标只要 0.11 秒**。可以忽略不计。

## 三、附带发现（有利条件）

### 快照与日线完全一致 ✅

抽样 80 只 → 扩到全量 306 只验证：

```
一致(<0.02% 偏差): 306    不一致: 0    缺失: 0
```

两个数据源（快照来自腾讯实时接口，日线来自历史 K 线接口）**口径完全统一**，
可以放心混用 —— 用快照的 `price` 当日线 `close` 的补充，或用日线做历史回溯。

### 数据完整度良好 ✅

```
有 >=  20 根日线的股票: 306 只    ← MA20 可用
有 >=  60 根日线的股票: 306 只    ← MA60 可用
有 >= 120 根日线的股票: 306 只
有 >= 250 根日线的股票: 305 只    ← MA250/年线 基本可用
不足 20 根的（新股/停牌）: 0 只
```

当前 sync 默认拉 500 根（≈2 年），足够覆盖 MA250/年线。

## 四、难点总结与最终状态

### 难点总结（改造后回填）

| # | 难点 | 严重度 | 最终状态 | 解决方式 |
|---|---|---|---|---|
| 1 | 覆盖率仅 8.1% | ⚠️ 需决策 | ✅ **已消除** | eltdx 全市场落库 → **5565 只 / 270 万条**，覆盖率 100% |
| 2 | 停牌 / 数据滞后 | ⚠️ 必须处理 | ✅ **已消除** | eltdx 适配器剔除停牌占位行（OHLC 全等 + volume=0）；引擎按最新交易日对齐 |
| 3 | 读取性能（逐只 17 分钟） | 🔴 已解决 | ✅ **已解决** | `history.py` 一次全表读（实测 3.3s） |
| 4 | 内存（dict 503MB） | ⚠️ 已解决 | ✅ **已解决** | numpy float32 → **26.7 MB**（5565 只 / 146 万行） |
| 5 | 全量加载 37.9s | 🔴 已解决 | ✅ **已解决** | 进程内缓存 + 按交易日失效；实测加载 **3.3s**（比预估快 10 倍，RTT 主导） |
| 6 | 指标计算 | ✅ 非问题 | ✅ **非问题** | 全市场全套指标 0.11 秒量级 |

**六个难点全部关闭，无需决策项。**

### 改造之外额外发现并修复的问题

这两个是**改造开始前没预料到**的，属于「准确性」层面的真实缺陷：

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 7 | **float32 边界比较** | 450 只突破新高里 **6 只是「平前高」被误判为「破前高」**（突破幅度 < 1e-6） | 新增 `_gt`/`_lt`/`_ge` 带容差比较（`EPS=1e-5`）；MA 求和提升到 float64。突破新高 450 → **444** |
| 8 | **区间振幅含当日** | `range60_pct` 把当日（放量大涨那根）算进去，振幅虚增 3~12 个百分点，**误杀合格平台突破** | 改为 `H[:-1]`（不含当日），与 `hhv60`/`llv20` 口径统一。平台突破 36 → **39** |

> 问题 8 的典型案例：`sh600640` 不含当日振幅 26.3%，含当日 38.2% —— 仅因窗口差一根，
> 就被 35% 阈值挡在门外。这是**语义错误**而非精度问题。

### 架构（实际落地）

```
新增 server/history.py                     ← 实际文件名（原计划 bars_cache.py）
├─ HistoryEngine.load()    # 一次 SQL 全表读（3.3s）+ numpy 分组，进程内缓存
├─ HistoryEngine.metrics() # 取某只的全套指标，数据不足返回 None
├─ HistoryEngine.screen()  # 批量筛选
├─ _gt / _lt  (EPS=1e-5)   # 带容差的边界比较（问题 7 的修复）
└─ get_engine() / reload_engine() / selfcheck()

改造 server/screener.py
├─ 6 个伪历史策略改为接收历史引擎（`hist=` 参数）
├─ 不传 `hist` → 返回空集（宁可不出结果，不给错结果）
├─ 新增 _gt/_lt/_ge 容差比较辅助
└─ 9 个纯当日策略零改动

改造 server/app.py
└─ /api/strategy_scan 返回 diag 字段（history_ready / history_as_of / needs_history）

改造 web/index.html
└─ 依赖历史的策略显示「日线」角标
```

### 关键设计决策（最终采用）

1. **保持纯当日策略零改动** —— 只有 6 个函数需要动，风险可控
2. **数据不可用时明确降级**，而非静默返回错结果：
   - 无引擎 / 不传 `hist` → 返回空集
   - 数据不足（< 60 根）→ 返回 None，策略跳过该股
   - 停牌占位行 → 在取数层就剔除
3. **返回结果附带 `diag`**，前端据此提示历史数据就绪状态与交易日
