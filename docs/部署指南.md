## 一、先说结论：怎么让朋友访问

**推荐路径 A（多人共享，最省事）**：配一个云端数据库，然后 `./deploy.sh start`。数据不在本机，朋友们访问任意一个运行中的实例即可，**可以跳过隧道**。

**推荐路径 B（纯本地）**：把整个 `tick-stock-panel/` 目录拷到你自己的电脑（或一台常开的机器），跑两条命令。

```bash
cd tick-stock-panel

# 第一条：启动服务（首次会自动建虚拟环境、装依赖）
./deploy.sh start

# 第二条：开公网隧道（会打印一个 https 地址，发给朋友即可）
./deploy.sh tunnel
```

第二条命令会输出形如 `https://xxxx-yyyy.trycloudflare.com` 的地址，把它发给朋友，他们打开就能用。

### 为什么不在我这个环境里直接开隧道

我实测过，这个沙箱**跑不了 Cloudflare Tunnel**：

| 检测项 | 结果 |
|---|---|
| 下载 cloudflared | `HTTP 000` —— GitHub 不可达 |
| `api.cloudflare.com` 解析 | `198.18.0.46`（保留网段，被代理层拦截，非真实节点） |
| 预装隧道工具 | cloudflared / ngrok / frpc / tailscale **均无** |

隧道客户端需要**长期稳定的出站长连接**并挂在你自己的 Cloudflare 账号下，这在当前沙箱里做不到。所以我把能做的全做了 —— 部署脚本、配置模板、说明文档，你只需在自己机器上跑两条命令。

## 二、三种访问方案对比

| 方案 | 命令 | 域名 | 访问控制 | 适合 |
|---|---|---|---|---|
| **纯本机** | `./deploy.sh start` | `127.0.0.1:8899` | — | 自己用 |
| **云端数据库** | 配 `.env` 后 `./deploy.sh start` | 取决于服务部署在哪 | 内置账号 | **多人长期用（推荐）** |
| **快速隧道** | `./deploy.sh tunnel` | 随机地址，**重启会变** | 无 | 临时给朋友看 |
| **具名隧道** | 见 `cloudflared.example.yml` | **固定** `tick.你的域名` | 可加邮箱验证 | 固定域名长期用 |

> 云端数据库解决的是「数据存哪」，隧道解决的是「别人怎么连进来」，两件事独立。
> 用了云端库之后，你可以把服务部署在任何能联网的地方，朋友们访问那个地址即可，不必再折腾内网穿透。

### 关于访问控制（重要）

你现在是「和几个朋友用」，有**两层防护**可选，建议叠加：

**第一层：应用内置账号**（已做好，开箱即用）

- 面板右上角「登录 / 注册」
- 每个账号的自选股、分组、虚拟盘**完全隔离**
- 密码用 PBKDF2-SHA256 加盐哈希存储（20 万次迭代），不存明文
- 会话走 httpOnly Cookie，30 天有效

**第二层：Cloudflare Access**（可选，推荐的加固）

- 在 Cloudflare 后台给域名加邮箱白名单
- 访问时要先输邮箱收验证码，通过才能进
- 好处：即使链接外泄，陌生人也进不来
- 配置步骤写在 `cloudflared.example.yml` 里

> **简单判断**：如果你只在朋友小群里发链接，第一层就够。如果链接可能被转发出去，建议把第二层也开上。

## 三、新增功能说明

### 1. 账号系统

| 项目 | 实现 |
|---|---|
| 注册 | 用户名 2-24 字符，密码至少 6 位 |
| 登录 | 支持 Cookie 和 `Authorization: Bearer` 两种方式 |
| 密码存储 | PBKDF2-SHA256，每用户独立随机盐 |
| 会话 | 30 天有效，过期自动清理 |
| 数据隔离 | 自选股 / 分组 / 持仓 / 流水全部按 `user_id` 隔离 |

**自选股不登录也能用** —— 数据挂在内置的本地账号下，适合自己一个人用的场景。登录后即切换到你的账号。

**虚拟盘必须登录**（守卫见 `server/app.py: _require_login`）。理由：虚拟盘会凭空产生资金与持仓，
匿名数据没法归属、也没法跨设备延续，认领逻辑会变得不可解释。

守卫上线前产生的匿名数据不会被丢掉，而是变成一份**待认领的遗产**：
登录后虚拟盘页会出现「认领到本账号」提示，点击即整体过户（先到先得，认领后匿名侧清空）。
**资金是替换而非相加**——否则每个登录的人都能白拿一次初始资金。

接口清单：

```
POST /api/auth/register    注册
POST /api/auth/login       登录
POST /api/auth/logout      退出
GET  /api/auth/me          当前用户
```

### 2. 虚拟盘

**简单版实现**：按实时价模拟成交，算持仓浮动盈亏。

| 规则 | 值 |
|---|---|
| 初始资金 | 100 万元 |
| 买入单位 | 100 股整数倍（1 手） |
| 佣金 | 万 2.5，单笔最低 5 元，双向收取（**按用户可调**） |
| 印花税 | 千 0.5，仅卖出（**按用户可调**） |
| ETF 费率 | 佣金单独可调；**印花税恒免**（税法规定，不做成可配项） |
| 成本口径 | **含手续费**（更贴近真实持仓成本） |

**费率按用户存**在 `users` 表的 5 个列里，注册时固化为当时的默认值，
之后各自在虚拟盘页的「费率设置」折叠区里改，互不影响。

**成交价口径会被记录下来**（`trades.pspan`），流水表里单独一列显示：

| 时段 | 留空成交的价 | 标记 |
|---|---|---|
| 9:30–11:30 / 13:00–15:00 | 当前最新成交价 | `实时` |
| 9:15–9:30 集合竞价 | 竞价撮合价 | `竞价` |
| 15:00 之后 | 当日收盘价 | `收盘` |
| 9:15 之前 / 周末 / 节假日 | **上一交易日收盘价** | `昨收` |
| 用户手填 | 用户填的 | `手填` |

标出来是必要的：收盘后 `quote_tencent` 照样返回数据，不标的话用户会以为
自己按"实时价"成交了，复盘时对不上真实行情。

**手填价有区间护栏**：必须落在该标的当前可成交的价格区间内，否则 400。
区间口径按市场状态分两路——盘中用**分钟线聚合当日 H/L**（日线是 15:30 才落库的，
盘中拿到的最后一根是"昨天"，用它卡今天会误拦），盘后/休市用最新一根日线的 H/L。
**取不到区间时放行**：宁可让用户填个离谱价，也不要因为一次网络抖动把正常买入拒掉。

这也意味着虚拟盘是**市价单模型**——不可能以一个当日从未出现过的价格成交，
所以填不了"挂 1200 等它跌"这种限价单，这是有意为之。

接口清单：

```
GET  /api/trade/positions   持仓（含实时价、市值、浮动盈亏）
GET  /api/trade/summary     账户总览（可用资金/市值/总资产/累计盈亏 + 现价口径）
POST /api/trade/buy         模拟买入（价格留空 = 实时价成交；手填价受区间护栏）
POST /api/trade/sell        模拟卖出（返回本笔盈亏）
GET  /api/trade/history     成交流水（含价格口径）
POST /api/trade/reset       重置账户
GET  /api/trade/fees        当前费率（含 defaults，供「还原默认」）
PUT  /api/trade/fees        改费率
GET  /api/trade/claim       是否有匿名数据可认领
POST /api/trade/claim       认领匿名数据（搬走制）
```

**前端入口**：`💰 虚拟盘` 页签，含资金概览卡片、费率设置折叠区、买入表单、
快捷标的按钮、持仓表（可直接加仓/卖出）、成交流水。未登录时整页显示登录遮罩。

**持仓表新增「建议止损」列**：吊灯止损价（见第 7 节），随波动率自动移动——
波动加大止损放宽、波动收窄止损收紧。现价已跌破该线时**标红**并显示"已破 x%"，
未跌破则显示"尚有 x%"。

这是**参考位不是指令**：只陈述"现价在不在止损线下"这个客观事实，不替用户做
卖出决定——成本、仓位、大盘都不在这个读数里。取不到本地日线（该票没落库）时
显示 `—`，**绝不用 0 冒充有效值**。

### 4. 网格回测（📊 回测 → 网格交易回测）

在 `中心价 ±上下界` 之间按 `步长%` 铺档，跌到买档买一份、涨到卖档卖一份。
输出收益 / 年化 / 最大回撤 / 夏普 / 卡玛 / **买入持有基准** / **K线买卖点图** / 净值曲线 /
档位表 / 成交明细。

**4 种网格策略**（「网格策略」下拉，默认固定）：

| 策略 | 可调参数 | 做法 | 适合 |
|---|---|---|---|
| **固定** `fixed` | — | 上下界固定，每格等份买、等份卖 | 区间震荡的基准打法 |
| **金字塔加码** `pyramid` | 加码倍率（默认 1.5，1~5） | 跌得越深买得越多（每远离基准一档 ×倍率，8 档封顶），卖出仍一格一份 | 判断是「震荡后还会回去」，想摊低成本 |
| **不对称** `asym` | 卖出步长（默认买步长 ×1.5） | 买入用小步长、卖出用大步长 → 攒筹码慢卖；反过来（买步长更大）就是快进快出 | 想让买卖两侧节奏不同 |
| **移动** `moving` | — | 价格跑出上下界后，区间整体跟随平移并重铺档位（持仓不动），解决单边行情「停摆」的固有缺陷 | 趋势/单边行情，不想中途停摆 |

参数框只显示该策略用得上的（选「不对称」才出现卖出步长、选「金字塔」才出现倍率）。
结果摘要行会标出策略与特征（如「移动网格（区间平移 2 次）」），warnings 里也会针对
策略给出提示（金字塔提示资金占用、移动网格提示平移次数与错过卖点的风险）。

**实测对比**（600195，250 根日线，步长 2%、区间 ±20%、资金 10 万，同一组参数只换策略）：

| 策略 | 成交 | 买/卖 | 网格收益 | 同期买入持有 |
|---|---|---|---|---|
| 固定 | 21 笔 | 11/10 | **+4.28%** | −10.86% |
| 金字塔（×1.6） | 16 笔 | 6/10 | +3.78% | −10.86% |
| 不对称（卖步长 5%） | 14 笔 | 11/3 | −2.65% | −10.86% |
| 移动（平移 2 次） | 35 笔 | 16/19 | +3.36% | −10.86% |

读法：不对称那组「卖出步长 5%」导致只卖出 3 笔（攒着不卖），区间一路向下就吃不到反弹；
移动网格成交最多（35 笔）——原网格早停摆了，它靠平移续命继续做。

**K 线买卖点图**：**红箭头朝上 = 买入**（浮在日柱下方）、**绿箭头朝下 = 卖出**（浮在日柱上方）。
锚点取当天的 `(开+收)/2`（日柱中价），再靠 `symbolOffset` 做 ±20px 像素位移浮到柱体外 ——
不压柱身，也不像贴影线端点那样飘在日柱之外。
同时画三条档位横线（上界 / 基准 / 下界），一眼看出价格跑到档位哪儿了。
同一根 K 线成交多笔时归并成一个标记，标记上的数字是笔数。悬停显示均价/份数/笔数。

> 两个踩过的坑，改这块时注意：
> 1. **别给 scatter 的 `value` 塞空字符串** —— echarts 会当数值 0 参与 y 轴范围计算，
>    实测把 4.4~5.0 的图硬撑到 y=2，买卖点全飘到图外。笔数放 `name` 里。
> 2. **`symbolOffset` 只在锚点本身落在数据带内时才安全**。早先锚点写在影线端点
>    （low/high）上再叠 offset，同样把 y 轴撑到 2。锚点用日柱中价就没事。
>
> e2e 里有对应断言兜底：锚点必须等于 `(开+收)/2`、必须带非零 offset、
> K 线全序列必须完整落在图内（`tests/e2e_etf_grid.py`）。

点「🎯 用 ATR 建议参数」可按 14 日 ATR 自动填步长与上下界。

比 grider 等外部实现多守的三条 A 股约束：

| 约束 | 说明 |
|---|---|
| **T+1** | 当天买入的份额当天不能卖（grider 是美股口径，完全没有这条） |
| **整手 100 份** | 每格份数自适应：`capital / 档位数 / 基准价`，向下取整到手，避免「买两格就没钱」 |
| **ETF 免印花税** | 按代码段自动判定（`sh5*` / `sz15*` / `sz16*` / `sz18*`） |

踩过的四个坑（都已在代码里注释说明）：

1. **加权成本不能靠总资产倒推**（grider 的算法实测失真 +50）→ 单独维护 `avg_cost`
2. **单根日线要允许先下后上双向成交**，否则一根大阳线吞掉卖单
3. **触发率 = 被触发过的档位 / 总档位**，不是「成交笔数 / 网格数」（后者会 > 1）
4. **拒单不推进指针** —— T+1 拦下的单要留在原档，推进指针会永久漏单

自检：`cd server && python3 grid.py`（9 段，含上面 4 个坑的回归 + 新策略 7 项：
固定等份 / 金字塔份数递增 [20000→40000→80000] / 倍率 1.0 退化成固定 /
不对称默认卖步长 = 买步长×1.5 / 自定义卖步长生效 /
移动网格单边行情下触发平移 / 移动网格成交多于固定）。

**必须知道的天花板**（单边行情实测，回测结果里也会报警）：

| 场景 | 行情 | 网格 |
|---|---|---|
| 单边上涨 | +81.67% | **+8.85%**（只成交 2 笔，突破上界停摆踏空） |
| 单边下跌 | -45.28% | **-40.08%**（一路买满，现金耗尽） |

网格是**震荡市**工具。趋势市里它一定跑输买入持有或亏得更狠。

### 5. 网格档位表（💰 虚拟盘 → 网格档位表）

把上面的档位铺到虚拟盘上，**不自动成交**，每档手动点「成交」按档位价下单，
走的是和手动买卖完全相同的 `store.buy_stock` / `store.sell_stock`，流水口径标记 `pspan=网格档位`。

- **方向由后端按档位下标与基准档的关系判定**，不信任前端传的 side
- 重复成交同一档 → 400；点基准档 → 400
- 档位本身**不落库**（由 `grid.build_levels` 实时算），库里只存参数 + 已成交档位下标 `fired`
- 未登录一律 401（跟虚拟盘同一守卫）

### 6. 自动刷新

导航栏右侧有开关，**默认开启**，可关闭（偏好存在浏览器本地）。

分级刷新策略，且**只在浏览器页签可见时生效**（切到后台不刷，省流量）：

| 页签 | 间隔 | 理由 |
|---|---|---|
| 市场榜单 / 我的自选 / 虚拟盘 / 个股分析 | 60 秒 | 实时行情 |
| 异动监控 | 3 分钟 | 中等频率 |
| 市场热点 | 5 分钟 | 热度变化慢 |
| 小白选股 | 30 分钟 | 与后台计算周期对齐 |
| 策略选股 / 回测 / 条件选股 / 对比 | 不自动刷 | 需手动触发，避免误跑重活 |

### 7. 波动率三件套：吊灯止损 / 布林挤压 / Ulcer·Z-Score

蒸馏自 `cinar/indicator` 的 `volatility` 包（`chandelier_exit.go`、`percent_b.go`、
`bollinger_band_width.go`、`ulcer_index.go`、`z_score.go`）。

**为什么只补这四个，而不是多抄几个指标**：它们都能直接落到操作上——
止损有具体价位、位置是连续量、回撤有痛感、偏离可度量。而趋势类指标（Aroon 等）
经实测在本项目数据上价值很低：**492 个有效交易日里只有 10 天是趋势日**（且全挤在
2025-04-07~09），近 120 天为 0——A 股不缺趋势指标，缺的是震荡市工具。

| 指标 | 公式 | 看什么 |
|---|---|---|
| **吊灯止损** | `HHV(High,22) − 3×ATR(22)` | 随波动率移动的多头止损线。波动加大止损放宽、波动收窄止损收紧 |
| **布林 %B** | `(C − 下轨) / (上轨 − 下轨)` | 0=贴下轨、0.5=中轨、1=贴上轨；突破时 <0 或 >1。把"触及上下轨"的二值判断升级成连续位置 |
| **布林带宽 + 分位** | `(上轨 − 下轨)/中轨 × 100`，再取近 120 根分位 | 分位越低越挤压（波动收缩），是**震荡市里少有的有信息量的信号** |
| **Ulcer Index** | 窗口内回撤百分比的 RMS | 与 Sharpe 的区别：Sharpe 用波动率（上下都罚），Ulcer **只罚下跌**且惩罚深度与持续，更贴近"套牢有多难受" |
| **Z-Score** | `(C − SMA20) / STD20` | 偏离均值多少个标准差。与形态匹配实测结论同向：A 股"越低、越缩量、前期涨得越少 → 未来越容易涨" |

布林口径与 `mytt.BOLL` 保持一致（SMA + **总体标准差** `ddof=0`），
否则同一只票在指标面板和 K 线图上会算出两条不一致的布林带。

**三个落点**：

1. **虚拟盘持仓表**新增「建议止损」列（吊灯止损价 + 距线幅度，跌破标红）
2. **个股 K 线主图**通道切换新增「吊灯止损」——一条橙色实线（实线区别于通道的
   虚线，语义上它是"该走的线"而不是区间边界）
3. **全套技术指标**新增「波动率」分组（6 项），指标总数 55 → **61**，
   分类 6 类 → **7 类**；并新增 3 条自动信号：突破布林上轨 / 跌破布林下轨 /
   带宽挤压（分位 ≤ 10）/ 跌破吊灯止损

**两个刻意的设计取舍**：

- 挤压**只给分位、不给布尔阈值**。"多窄算挤压"没有公认标准，且不同票的带宽量级
  差很多，硬编码阈值只会误报。
- 吊灯止损**不做"只上不下"的棘轮版本**。`cinar` 原式是原始口径，止损线会随 22 日
  高点过期而下移；叠在 K 线上看趋势更直观，改棘轮会丢掉这个可读性。
- 口径统一：持仓列 / K 线图 / 全套指标三处都取 **250 根日线**。取少了 Wilder ATR
  预热不足，会出现"K 线图 1274.34、持仓列 1273.66"这种同源不同值的坑（已踩过并修）。

**第四个落点：选股策略「布林挤压」**（策略目录 → 经典指标）。带宽处于近 120 日
最低 10% 分位的票会被选出来——挤压不指方向，**配放量突破确认使用**，别单独当买点。
阈值 `squeeze_pct` 可调（走查回测 / 参数覆盖都能改）。

实测：全市场 5575 只命中 **1057 只（约 19%）**，比"10% 分位"字面上的 10% 高一倍。
原因是**市场整体处在波动率收缩期**（此前实测近 120 天 0 个趋势日、Chop 66.6），
很多票的带宽都处在自身历史的低位——分位是「跟自己过去比」，全市场一起挤压时
命中自然变多。这是真实市况，不是阈值失效；想要更严就把 `squeeze_pct` 调到 5
（实测约 13%）。

**没进策略体检白名单**：它的作用是筛出候选票，历史超额收益还没测过。体检表每加
一行都是全市场 × N 天的开销，没测过的别占位——等走查回测验证过再补。

### 13. 同步守门三重判断 + 词典情绪分析（借鉴 qs / go-stock）

**同步守门**（`scripts/sync_bars.py` 的 `gate_full_sync`，蒸馏自 qs 智能更新）：
全量同步前按成本从低到高跑三重判断，任一命中即短路（`--force` 全部可绕）：

| 判断 | 依据 | 拦什么 |
|---|---|---|
| ① 时间守门 | 工作日 15:00 前且全量（all/snapshot/>1000 只） | 盘中落库写入**半根日线**，污染回测/体检 |
| ② 当日标记 | `data/update_cache.json` 同日同 scope 已成功 | 同一天重复打几千次请求 |
| ③ 覆盖率抽检 | 抽 100 只查 `max(date)`，≥90% 已到「期待日」 | 库里已最新还整段重拉 |

- 期待日 = 最近一个「可能已结算出日线」的工作日（15:00 前算昨天；不维护
  节假日表，节假日误期待只会白拉一次，方向宁拉勿漏）；
- 判断②只在 `fail==0 且 ok>0` 时写入——预筛全跳过（ok=0）不算成功，
  否则缺口当天再也补不上（真实踩到）；
- CLI：`python3 scripts/sync_bars.py --scope all`（守门自动生效），
  `--force` 绕过，`--no-incremental` 关闭增量预筛；
- 管理页手动落库（`/api/admin/bars/sync`）同样走守门，跳过原因写进任务 note。

**增量预筛**（`sync_via_eltdx` 阶段0，默认开启）：同步前查 `store.bars_progress()`
（每股 `max(date)` + 根数），已到参考日的整只跳过、历史不足的整段拉、
只落后几天的按「缺口天数+3」拉。参考日 = `max(库内众数, 守门期待日)`——
只看众数会与判断③打架（判断③说缺周五的线、预筛却因"全库已到周四"整体跳过，
缺口永远补不上，2026-09-26 周六真实踩到，用例已锁死）。实测：全市场重复
同步从 5575 只整段（16s 取数 + 分钟级落库）降到零请求或缺口档少量。

**词典情绪分析**（`server/sentiment.py`，蒸馏自 go-stock `stock_sentiment_analysis.go`）：
纯本地零成本给文本打「看涨/看跌/中性」：

- 正/负金融词各 35 个（权重 1.5~3.0）+ 否定反转 + 程度乘数（非常 1.8 /
  极其 2.2 / 小幅 0.7 …）+ 转折后段 ×1.5（但是/然而/不过/却/可是）；
- **免分词设计**：词典词直接在原文 `find()` 定位（长词优先，防「创新高」
  再吃一次「新高」），比 gse/jieba 分词更稳（分词会把「创新高」切碎丢词）；
- 相对 go-stock 的一处增强：否定窗口扩到情绪词前 3 字逐字找
  （中文否定常带衬词：不【进行】分配、未【出现】好转、无【重大】利好）；
  程度词整体优先于逐字否定（否则「非常」的「非」会被误当否定）；
- 阈值：score > +1.0 看涨 / < -1.0 看跌 / 其余中性；
- 挂载：`/api/notices` 每条公告自动带 `sentiment` 字段，前端公告列表加
  ▲看涨（红）/ ▼看跌（绿）/ ─中性（灰）徽章，与 #12 的风险着色并存
  （徽章=情绪方向，标题颜色=风险警示）；`POST /api/sentiment {"texts":[...]}`
  通用批量端点留给快讯流/自选分组聚合复用；
- 词典法的固有天花板：**「不看好」会判成正面**（不+看空 → 反转），要彻底
  解决得上 LLM（#93 的活），词典法只求把 80% 常见表达判对。

实拍见 `docs/shot-sentiment-badge.png`（五粮液「集团增持」公告 ▲看涨 +2）。

## 四、数据库说明

支持**两种后端**，运行时由 `.env` 决定，代码和调用方完全一致：

|---|---|---|---|
| **SQLite**（默认） | 没有 `.env`，或 `.env` 里没写 `TICK_DB_HOST` | 本机 `data/tick.db` | 自己一个人用 |
| **云端 MySQL 协议库** | `.env` 里填了 `TICK_DB_HOST` | TiDB Cloud / MySQL / MariaDB | 多人共享、多设备切换 |

### 切到云端数据库（推荐多人用）

```bash
cp .env.example .env
# 编辑 .env，填入主机、端口、用户名、密码
./deploy.sh start
```

已实测兼容 **TiDB Cloud Serverless**（`8.0.11-TiDB-v8.5.3-serverless`，MySQL 8.0 协议）。
这套后端最大的价值是：**服务放哪台机器都行，甚至换机器，数据都在同一个云端库里**，
于是前面那个 Cloudflare 隧道就不是必需的了 —— 朋友们访问任意一个在跑的实例即可。

### 切回本地

把 `.env` 里的 `TICK_DB_HOST` 注释掉（或删掉 `.env`）即回落到 `data/tick.db`。
**本地数据不会被删除**，两边可以随时来回切。

### 从本地迁移到云端

```bash
# 确认无误后加 --apply
```

脚本会保留原主键 ID（父子关系不错位），写入前清空目标表因此可重复执行，

### 日线落库的每日自动调度

服务内置（不是 cron），每天 `TICK_SYNC_BARS_AT`（默认 15:30）把全市场日线写入
`daily_bars`。状态存在 `meta` 表，所以**服务重启后仍知道"今天跑过没"**——
漏跑会自动补，不需要额外的补跑逻辑。

**交易日判断用多源交叉**（见 `server/scheduler.py: is_trading_day`），
不维护节假日表（那玩意儿要逐年更新，调休每年不同）：

| 源 | 依据 | 特点 |
|---|---|---|
| ① 实时快照 | 腾讯快照的行情时间戳 `time` | **最灵敏**——15:00 收盘即带上今天日期 |
| ② 日线 | 最新一根日期 | 最权威，但要等结算，滞后 |
| ③ 分钟线 | 最后一根日期 | 实时（eltdx 优先） |

规则是**一票肯定制**：任一源证明"今天有行情"即交易日；只有所有源都明确说
"今天没数据"才判非交易日。三个源都取不到时返回 `None` → **照跑**（宁可白跑一次，
也不能因一次网络抖动整天不落库）。

**落库成功后的固定动作**（定时、管理页手动、调度立即跑三条路径一致）：

1. `history.reload_engine()` —— 落库只写了 SQLite，内存历史引擎还停在旧数据；
   不重载的话，体检/选股要等到服务重启才能看到当天数据。
2. `strategy_eval.prewarm()` —— 后台线程用默认参数（120 天 / 未来 5 日）重算
   一次策略体检并写入缓存。第二天打开「策略体检」直接是现成结果，不用等两分钟。
   同参数当天只预热一次；服务若在落库后才重启，启动时会补跑（今天没落库则跳过）。

手动验证钩子链路（mock 落库，不碰真实行情）：`python3 tests/check_prewarm_hook.py`。

> **这修掉了一个真实的静默失败。** 最早只用日线，逻辑是「最新日线 != 今天 → 非交易日」，
> 这句话把「节假日」和「盘后数据尚未出」混为一谈。每天 15:30 恰好落在后者：
> 日线还没结算出当日那根，于是**整天被跳过，而那天明明是交易日**。
> 把快照提到第一位就是为了补这个滞后——它在 15:30 那一刻必然已经更新。
>
> 残留天花板：若快照恰好挂了、且日线与分钟线同时停在昨天，仍会误判。分钟线是
> 实时的，交易日 15:30 必然有当天数据，所以这需要三个源一起出问题；真发生了也
> 只是漏跑一天，下次会补。

> 两端的少数 SQL 方言差异已封装在 `server/store.py` 内：占位符 `?`→`%s` 驱动层自动改写，
> `ON CONFLICT`→`ON DUPLICATE KEY UPDATE`、`last_insert_rowid()`→`LAST_INSERT_ID()`、
> `BEGIN IMMEDIATE`→`SELECT ... FOR UPDATE` 各有分支。业务代码一律写 SQLite 风格 `?`，不用锅炉了。

### 备份

**推荐：后台管理 → 💾 系统备份 → 「立即备份」**。在线一致备份（SQLite `backup()` API，
读穿 WAL），**服务不用停**，备份落在 `data/backups/tick_时间戳.db`，页面上有清单。
恢复 = 把文件拷回 `data/tick.db` 后重启服务（页面上刻意不提供一键恢复，避免误点）。

命令行方式（适合写 cron）——SQLite 就一个文件，但**服务运行中直接 cp 有风险**
（可能拷到写到一半的状态），要么停服再拷，要么用 Python 在线备份：

```bash
# 服务停止后：
cp data/tick.db ~/tick-backup-$(date +%F).db

# 服务运行中（在线一致）：
python3 -c "import sqlite3; s=sqlite3.connect('data/tick.db'); d=sqlite3.connect('backup.db'); s.backup(d)"
```

云端库建议在控制台开启备份策略；本地的 `data/tick.db` 始终是一份完整副本，别忘了它。

**做什么**：策略选股页签新增「🩺 策略体检」按钮。点击后用历史日线逐个回算
**15 个可回算日线策略**（含方案 A 新增的 6 个经典指标策略）的有效性——把

**收益窗口可选**：面板里可切 1 / 3 / 5 / 10 / 20 日（默认 5 日）。
短窗口看短线爆发力，长窗口看趋势延续性——同一个策略在不同窗口的结论
可能完全不同（这正是切换的意义）。每个窗口独立缓存。

**命中超额列**：命中股日均收益 − 其余股日均收益（费前）。
回答「照着买能不能占到便宜」：正=命中后确实更好（红），负=命中后反而更差（绿）。
鼠标悬停可看命中组均值、其余组均值与命中胜率。

**市况敏感度列（方案 D）**：把每个交易日的全市场市况打上标签（趋势市 /
震荡市 / 过渡市，口径见下节「市况开关」），命中超额分别在两种市况里各算
一遍。回答「这个策略在什么行情下才灵」：趋势类策略看「趋势」那一格，
反转/形态类看「震荡」那一格；任一侧观察样本 <10 显示 —（防小样本噪声），
悬停可看两组超额与观察样本数。实测见下节。

**分层测试（pattern_score 专属）**：形态评分是 0~100 连续分数，每天按分数
等频切 5 组（G1 最低分 → G5 最高分），看各组未来收益是否随分数单调走高。
比 IC 更直观：IC 说"有相关"，分层说"分数怎么用"。
实测（40 日窗口）曾出现 G4 > G5 的非完美单调（单调度 0.7）——提示极端
高分形态反而回落，分数适合两头用而非线性外推。

> 曾出现 −0.6 上下的强反向 ICIR，说明窗口选择会显著改变结论，这也是体检
> 面板允许切换收益窗口的意义。

`breakout_20h`/`ma_bull` 这类经典策略在 A 股短线窗口普遍是弱/反向指标——这与
`docs/形态匹配说明.md` 的独立实测（167,721 观察点）方向一致。界面上
反向策略标绿色「⚠️反向」，卡片徽章用 A 股配色（正向红、反向绿）。

**只评 15 个的原因**：`daily_bars` 没有 `turnover`（需流通股本）、
`total_cap`（需总股本）、`name`（ST 判定），其余 7 个日线策略依赖这些
字段，无法从日线重建。**不做代用指标**（如用成交量排名冒充市值）——
口径不严谨的 IC 会误导使用。界面会列出每个跳过策略的具体原因。

**性能**：15 策略 × 120 天约 240~330 秒（其中 ConnorsRSI / SuperTrend 等
经典指标含 Python 循环，是主要增量；结果按（天数, 收益窗口, 数据版本）
缓存 6 小时，二次访问毫秒级。建议日常以 40 天窗口体检，约 80 秒）。

**核心坑（时序错位）**：第一版把完整历史引擎传给策略函数，
而 `history.HistoryEngine.metrics()` 用 `C[-1]` 取最后一根——导致每天
算的都是「最新交易日」的指标。症状是 `breakout_20h` 日均命中 2005 只
（正常 300~400），IC 算出 −0.19 的假信号。修法：`_TruncatedEngine`
把序列切到目标日。切片正确性已用「手工算 ma20 与引擎输出比对」验证。
`server/strategy_eval.py` 自检 22 步覆盖此坑（含 `np.ones` 秩陷阱：常量
序列 argsort 后秩仍有方差，必须先查输入 std 而不是秩的 std）。

### 模拟净值 + 市场宽度（`tests/e2e_sim_breadth.py`）

方案 3（模拟净值）与方案 4（市场宽度）的端到端测试。

> **跑之前先看这里**：本脚本要的是 **days=120** 的体检结果（依赖服务启动预热），
> 而体检缓存 `_HITS_CACHE` 是**单槽**（按 `days|forward|as_of` 整份替换）。
> 所以**先跑过 `e2e_strategy_eval.py`（它全程只用 days=40）就会把 120 挤掉**，
> 于是「模拟 API / 曲线 / 指标 / 笔数」4 条一起挂——这是顺序依赖不是功能坏了。
> 正确顺序：单独跑本脚本（先确认 120 天预热已完成，或手动
> `POST /api/strategy_eval/job?days=120&forward=5` 预热完再跑，约 230s），
> 之后再跑 `e2e_strategy_eval`。

**模拟净值（方案 3）**：体检面板下部新增「模拟净值 · 跟着买回放」。
它模拟「每天照着信号买、等额分钱」的真实钱包曲线，规则全部写死透明：

1. 信号日收盘后才看到信号 → **次日开盘等权买入**（无未来函数）；
2. 次日**开盘涨停买不进**自动跳过（主板 9.8%/创业科创 19.8%/北交 29.8%
   开盘价阈值；库里无 ST 标记，ST 实际 5% 会漏判，口径详见
   `equity_sim.limit_ratio`）；
3. 持有 3/5/10 个交易日后收盘卖出（按个股自己的日历，停牌自然顺延）；
   数据尾部未平仓的按最后收盘价估值（计入 n_open）；
4. 双边费率 15bp（买入 7.5 + 卖出 7.5）；
5. 组合日收益 = 当日活跃持仓的等权平均，空仓日走平；
6. 基准为**全市场等权**（闭眼随机买），不是沪深 300——库里没有指数日线，
   且策略命中集合本身等权，等权基准更公平。

红线 = 策略净值，灰虚线 = 全市场等权；指标行在原有的「窗口总收益 / 同期全市场
/ 超额 / 年化(估) / 最大回撤 / 逐笔胜率 / 笔数 / 涨停跳过数」之外，方案 B
又补了 4 个**回测质量指标**（蒸馏自 `cinar/indicator` 的 sharpe_ratio /
sortino_ratio）：

- **Sharpe（年化）＝ mean(日收益) / std(日收益) × √250**。无风险利率取 0。
  >1 良好、>2 优秀；窗口短（如 40 天）样本少，标注「窗口短仅供参考」。
- **Sortino（年化）**＝ mean / 下行 std × √250。只罚亏损波动，适合看重
  回撤的小白——同样收益下波动更「干净」的策略 Sortino 更高。
- **Calmar** ＝ 年化收益 / |最大回撤|。越高说明「用回撤换收益」越划算。
- **盈亏比** ＝ 平均单笔盈利 / 平均单笔亏损。× 胜率 ≈ 期望收益，是比
  胜率更完整的盈亏画像。

> 防 0/0：当日收益序列 std≈0（直线）时 Sharpe/Sortino 退化为 `None`，
> 而不是把「无波动直线」误判成超额收益。

**性能优化（方案 B 顺带修）**：模拟净值的「全市场等权基准曲线」原先用
`np.add.at` 做按日 scatter 累加，全市场 ~5569 只 × ~500 日会让首次模拟
卡 30s+。改用向量化的 `np.bincount` 后，首次计算也 < 1 秒，冷启动的模拟
请求不再超时。

**为什么它和体检的「命中超额」不一样**：体检以 T 日收盘价为基准算
未来收益（信号的信息含量）；模拟以 T+1 开盘追入（真实执行成本）。
突破类策略 T 日大涨、次日高开追入会吃掉大段收益——两者差异本身就是
「信号好不好」与「追进去还剩多少」的区别。实测（120 日窗口）：
`oversold_rebound` 体检超额 +1.47% → 模拟超额 +5.49%（正超额策略真实
买得到）；`breakout_20h` 体检 −0.12% → 模拟 −3.91%（方向一致、追高更差）。

**前置条件**：模拟复用体检产出的命中序列（`strategy_eval._HITS_CACHE`，
与体检缓存同生共死）。同参数体检没跑过时接口返回 409 + need_eval，
前端引导先体检——**绝不悄悄触发 40 秒重算**（防 504）。模拟本身纯内存
计算，毫秒级返回。

**市场宽度（方案 4）**：市场榜单页签「市场温度」下方新增「市场宽度」
卡片——市场的健康档案：

- **涨跌家数**（红涨绿跌，近 120 日差值柱状图）：赚钱效应的广度；
- **站上 20 日线比例**（250 日折线，20/50/80% 参考线）：中期趋势底盘；
- **60 日新高/新低家数**：多头的后排与伤兵营，指数新高但新高家数萎缩
  = 背离；
- **近似涨停/跌停家数**（收盘口径，含 ST 漏判，看趋势不看绝对值）；
- **市况读数 + Chop 震荡指数**（方案 D）：摘要行末尾标出今日市况
  （如「市况 震荡市 (Chop 67)」，趋势市红/震荡市紫/过渡市灰），卡片底部
  新增紫色 Chop 折线（近 250 日，0~100，38.2 趋势线 / 61.8 震荡线两条
  参考线）——持续走高 = 横盘震荡、趋势策略吃力；走低 = 单边趋势、
  突破/均线类更顺手。口径见下节「市况开关」。

**极值分位提示**：站上 20 日线比例处于一年内 ≤5% 分位 → 🧊 极端恐慌
（历史上常在阶段底部附近）；≥95% 分位 → 🔥 过热（追高容易买在短期高点）。
平时用于确认趋势与背离，极端读数做反向参考。

**性能**：宽度首次全市场聚合约 1.2s（引擎已加载时）+ 引擎冷加载约 10s，
按数据版本缓存后毫秒级。注意：服务刚重启时若与体检预热补跑（约 100s）
撞车，首次请求可能被拖慢——等预热结束再刷新即可。

**自检**：`server/equity_sim.py` 23 步（费用拆腿、涨停跳过、持有期、
强平、回撤、胜率、板块涨停比例、Sharpe/Sortino/Calmar/盈亏比 4 项质量指标）；
`server/market_breadth.py` 15 步（涨跌平/涨跌停/MA20/新高新低计数、百分位、
市况标签/Chop 定性/前 14 天占位）。

**端到端**：`tests/e2e_sim_breadth.py` 30 步全通过（API 直测 + 页面交互，
0 JS 报错；含方案 D 的市况读数与 Chop 折线断言）。效果截图见

### 市况开关（方案 D）：Chop 震荡指数 × 策略市况分桶

蒸馏自 `cinar/indicator` v2.1.44 的 `volatility/chop.go`（Choppiness
Index，Dreiss 震荡指数），回答一个此前缺位的问题：**当前是趋势市还是
震荡市？手里的策略适不适合这种行情？** 方案 A 把指标搬了进来、方案 B
把回测质量搬了进来，方案 D 把「行情环境」搬了进来。

**为什么用合成指数**：库里没有指数日线（`daily_bars` 只有个股），方案 D
用横截面**等权日收益均值**合成全市场指数：`P[t] = P[t-1] × (1 + mean_r[t])`；
High/Low 用当日「典型波动」`mean|r|`（全市场日收益绝对值的均值，约 1.x%，
是指数真实日摆幅的代理）生成。它是**波动结构的代理**而非可交易指数，
仅供市况定性，界面与文档都明确标注「合成口径」。

**Chop 公式**（n=14，TR 用前收，与 chop.go 逐行对齐）：

```
TR[t]   = max( High−Low, |High−prevClose|, |Low−prevClose| )
CHOP[t] = 100 × log10( Σ(TR,n) / (max(High,n) − min(Low,n)) ) / log10(n)
```

- 分子 Σ(TR,n) 是最近 n 天真实波幅之和（**总波动**），分母是 n 天
  最高最低价差（**净位移**）。区间内来回折腾 → 分子大分母小 → Chop 高；
  单边直行 → 分子≈分母 → Chop 低。区间价差为 0（极端横盘）时定义为 0。
- 阈值取经典斐波那契位：`<38.2 趋势市`、`>61.8 震荡市`、之间为**过渡市**
  （不参与趋势/震荡对比，只进主超额）。前 14 天占位 None。
- 实现于 `server/indicators_extra.py` 的 `chop_series()`（纯 numpy）。
  关键坑：HH/LL 滑动窗口必须与 ΣTR 的窗口**严格对齐**（ΣTR 从 bar1 起
  累计，HH/LL 就要从 bar1 起窗）——第一版从 bar0 起窗导致窗口错位，
  锯齿震荡反而算出低 Chop（定性反转），自检当场抓住，已修。

**策略市况分桶**（`server/strategy_eval.py`）：体检聚合时把每天的
命中/其余收益按当日市况标签分桶，每个策略多出
`regime = {trend_excess, range_excess, fav, trend_obs, range_obs}`。
任一侧观察样本 <10 时该侧返回 None（防小样本噪声），两侧都有值时
`fav` 标出占优一侧。分桶只是查表归堆，不增加可见耗时；regime 序列
按数据版本缓存（`_REGIME_CACHE`），宽度卡片与体检表复用同一份，
口径完全一致。

**实测结论**（2026-09-24 数据，Chop 序列 2024-08-26 ~ 2026-09-24
共 506 个交易日，前 14 日占位、有效 492 天）：

- 全历史分布：**震荡市 290 天 / 过渡市 192 天 / 趋势市仅 10 天**——
  仅有的 10 个趋势日全部集中在 2025-04-07 ~ 04-09，此后再无。近 120 天
  **0 个趋势日**（30 过渡 + 90 震荡，Chop 49.3~80.9，最新 66.6）。
  这解释了此前的老疑问：为何趋势类策略（突破新高/均线多头）在这个库里
  长期跑不出正超额——**不是策略退步，是根本没有趋势行情可吃**。
- 震荡市内命中超额（120 天窗口，未来 5 日）居前：跳空强势 +2.46%、
  超跌反弹 +2.04%、ATR突破 +1.77%、形态评分 +0.57%；趋势类的
  突破新高 +0.47%、均线多头 +0.04% 贴地——**反转/形态类吃震荡市、
  趋势类吃不到**，与市况标签自洽，也和 40 天截图一致（超跌反弹
  震荡 +5.08% vs 均线多头 −3.16%）。
- 趋势市一侧因 0 样本全部显示 —：**这不是缺陷而是结论**——当前没有
  趋势行情可回测，趋势策略的「趋势市超额」暂时无从验证；等库内再出现
  趋势日（Chop <38.2）该列会自动开始积累样本。

**前端**：体检表新增「市况敏感度」列（趋势/震荡超额，红绿着色 +
→xx 占优，悬停看样本数）；宽度卡片摘要行新增市况读数 +
底部 Chop 折线（38.2/61.8 参考线）。

**自检与端到端**：`indicators_extra` 29 步（Chop 6 步：横盘=0 / 平滑
趋势 <38.2 / 锯齿震荡 >61.8 / 定性正确 / 末值版一致 / 数据不足 None）；
`market_breadth` 15 步（市况标签、Chop 定性、占位 None）；`strategy_eval`
22 步无回归。e2e：`e2e_strategy_eval` 29 步（含市况列 15/15 行有值）、
`e2e_sim_breadth` 30 步（含市况读数、Chop 折线）。截图：
`docs/shot-strategy-eval-d.png`（市况敏感度列）、
`docs/shot-breadth-d.png`（市况读数 + Chop 震荡指数）。

## 六、已知限制

| 限制 | 说明 |
|---|---|
| 沙箱内无法开隧道 | 见第一节，需在你自己的机器上跑 `./deploy.sh tunnel` |
| 行情仅交易时段有效 | 非交易时段涨幅普遍为 0，策略选股可能扫不出结果 |

| 无找回密码 | 简单版未做邮箱验证，忘了密码只能直接改库 |
| 自动刷新不刷策略选股 | 有意为之 —— 避免后台误跑重活 |
| 吊灯止损在弱势市里会大面积"触发" | 它是趋势跟踪型止损（止损线 = 22 日高点 − 3×ATR），**下跌行情中多数票都会跌破**。这是指标的正常行为，不是计算错误；用法上更适合"已经按趋势持有、需要一个离场位"，不适合拿它当抄底信号 |
| 建议止损依赖本地日线落库 | 没跑过同步的票显示 `—`（不是 0）。跑一次管理后台的日线同步即可 |

## 八、常见故障排查

### 1. 线上地址打不开（超时）

**症状**：浏览器一直转圈，但 `curl` 本地 `127.0.0.1:8899` 正常。

**根因**：服务监听的端口和平台配置的端口不一致。平台读 `.cloudstudio` 里的 `port`，
若服务实际listen在别的端口，网关就永远连不上。

**排查**：
```bash
ss -ltnp | grep 8899          # 看端口有没有在听、哪个进程在听
cat .cloudstudio              # 看平台要求的端口
```

**修复**：确认 `deploy.sh` 里的 `PORT`、`run.py` 的 `DEFAULT_PORT`、`.cloudstudio`
三处端口一致（当前统一为 **8899**）。然后：
```bash
./deploy.sh stop && ./deploy.sh start
```

### 2. 管理后台进不去（登录成功但没有「后台管理」入口）

**症状**：账号能登录，管理页签/入口消失，接口返回 403 `需要管理员权限`。

**根因**：管理员身份不落库，由环境变量 `TICK_ADMIN_USERS` 决定（见 `.env`）。
历史上只有 `deploy.sh` 启动时 `source .env` 注入该变量；若进程被裸起
（`python run.py`、平台自动重启），变量就丢了 —— 页面不报错，只是入口消失，很难定位。

**排查**：
```bash
curl -s -b <cookie> http://127.0.0.1:8899/api/admin/whoami
# admins_configured=false → 进程没读到配置
tr '\0' '\n' < /proc/<pid>/environ | grep TICK_ADMIN_USERS
```

**修复**：`server/app.py` 启动时已自带 `.env` 兜底加载（`_load_env_file()`，
不覆盖已有环境变量），确认 `.env` 里有 `TICK_ADMIN_USERS=admin` 后重启即可：
```bash
./deploy.sh stop && ./deploy.sh start
```
改管理员名单需要**重启进程**才生效。

> 跑 `tests/e2e_admin.py` 时若 admin 密码不是默认的 `test1234`，用
> `ADMIN_PASSWORD=实际密码 python3 tests/e2e_admin.py` 覆盖。

### 3b. CLI 落库报 `database is locked`（且 WAL 文件几百 MB）

**症状**：`python3 scripts/sync_bars.py` 落库全部失败 `OperationalError:
database is locked`（每只等锁 ~10s）；`data/tick.db-wal` 长到几百 MB 不收缩；
但 8899 服务本身一切正常，`py-spy dump` 看不到任何线程在碰 SQLite。

**根因**：服务进程里某个 SQLite 连接挂着**未提交的写事务**（线程 idle 但
事务不 commit/rollback），把写锁和 WAL checkpoint 一起僵住。09-24 的全市场
同步写入（272 万行）因此全部堆在 WAL 里（实测 228MB）从未合并回主库。

**修复**（2026-09-26 已实际操作过一次）：

```bash
kill <8899的pid>                        # 清掉所有连接
python3 -c "import sqlite3; \
  c=sqlite3.connect('data/tick.db', timeout=10); \
  c.execute('PRAGMA wal_checkpoint(TRUNCATE)'); c.close()"
# 输出 checkpoint 完成、tick.db-wal 消失即成功——WAL 里的数据已合并，绝不删 WAL 文件
nohup .venv/bin/python server/run.py >> server.log 2>&1 &
```

**预防**：跨进程写库（CLI）与服务进程共享 SQLite 时，尽量在服务低负载时跑
同步；守门判断③的抽检读操作不受锁影响（WAL 读写不互斥），只有写会撞。

### 3. 策略体检报 HTTP 504

**症状**：点「策略体检」后一会儿弹出 `评估失败：HTTP 504`，本地却一切正常。

**根因**：一次评估要跑上百秒（15 策略 × 120 交易日 × 约 5569 只，实测约
240~330 秒；日常用 40 天窗口约 80 秒）。外网域名中间的网关通常 60 秒就掐断
长连接，浏览器拿到 504，而服务其实还在算。

**修复**（已内置）：体检走「提交任务 + 轮询」——
`POST /api/strategy_eval/job` 秒回 job id，前端每 2 秒查
`GET /api/strategy_eval/job/{id}` 拿进度（进度条 + 已算到哪天），算完自动渲染。
单次请求都是亚秒级，任何网关都掐不断。切走页面再回来会接着算，同一份结果缓存 6 小时。
同步接口 `GET /api/strategy_eval` 仍保留给脚本调用，但浏览器端请勿直连它。

> 历史坑：`run.py` 默认端口曾是 8000，而不带参数启动时会落回 8000，
> 与平台要求的 8899 不符，导致线上 502/超时。已改为 8899。

### 2. `./deploy.sh stop` 后服务还在跑

**症状**：`stop` 提示已停止，但端口仍被占用、页面还能访问。

**根因**：`.run/server.pid` 里记的 PID 不是真正的监听进程（历史上用
`nohup ... & echo $!` 记的是子 shell 的 PID）。

**修复**（已内置）：`deploy.sh` 现在用 `ss -ltnp` 按端口反查真实 PID，
`stop` 会先杀 pid 文件里的进程，再按端口兜底清理；`start` 也会在启动前
清掉占用端口的残留进程。

若需手动处理：
```bash
ss -ltnp | grep 8899                    # 拿到真实 PID
kill <PID>; rm -f .run/server.pid       # 杀掉并清 pid
```

### 3. K 线主图上均线/通道"只画一半"

**症状**：K 线本身画满整个横轴，但 MA5/MA10/MA20/MA60（或布林/唐安奇/肯特纳
通道）从左到右只画了前面约一半就断掉。

**根因**：**后端指标序列被截断**，长度小于 K 线数量。ECharts 的 x 轴是
category 类型，series 按数组索引逐一对位；若 series 只有 120 个点而 x 轴有
251 个，就只能画出前 120/251 ≈ 48%，渲染上表现为"画一半"。

**修复**（已内置）：
- `server/indicator.py` 的 `compute_indicators()`：序列长度改为跟随 K 线
  （原先硬编码 `_lst(arr, 120)`、`dates[-120:]`），现在用 `n = len(klines)`。
- `server/indicator.py` 的 `channel_series(klines, n=None)`：`n` 默认取
  K 线长度，不再固定 120。
- `web/index.html` 渲染主图前增加 `alignTo(arr, n)` 兜底：series 比 x 轴长
  则取尾部、短则在头部补 `null`，即使将来两边长度再次不一致也不会错位。

**自检脚本**（改完指标逻辑后跑一遍）：
```bash
.venv/bin/python -c "
import json,urllib.request
K=json.load(urllib.request.urlopen('http://127.0.0.1:8899/api/kline?code=sh600519&period=day&count=250'))
kl=K['klines']; s=K['indicators']['series']; ch=K.get('channels') or {}
bad=[k for k,v in list(s.items())+list(ch.items()) if isinstance(v,list) and len(v)!=len(kl)]
print('K线',len(kl),'| 长度不一致字段:', bad or '无')
print('日期对齐:', [k['date'] for k in kl]==s['dates'])
"
# 期望输出： K线 251 | 长度不一致字段: 无   /   日期对齐: True
```
