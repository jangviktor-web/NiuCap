## 〇、一句话结论

**三个项目是三个不同方向，没有一个是「更完整的我们」**：

| 项目 | 方向 | 与我们的关系 |
|---|---|---|
| a-share-quant-selector | **单策略深度打磨**（碗口反弹 + B1 图形匹配） | 可借鉴**图形相似度匹配** |

## 一、项目 A：a-share-quant-selector

### 1.1 是什么

基于 akshare 的 A 股量化选股系统，**只做一个策略**——「碗口反弹」，
但把这个策略做到了工程化的深度。

**技术栈**：Python 3.8+ / akshare / pandas / numpy / matplotlib / Flask / 钉钉机器人
**许可证**：MIT
**数据存储**：CSV 文件（`data/` 目录）

### 1.2 优点

**① B1 完美图形匹配（最值得借鉴的点）**

基于 10 个历史成功案例做**四维相似度匹配**：

| 维度 | 权重 | 方法 |
|---|---|---|
| 双线结构 | 30% | 趋势线与多空线的相对位置、斜率、发散程度 |
| 量比特征 | 25% | 成交量变化模式（缩量后放量、持续放量等） |
| 价格形态 | 25% | 归一化价格曲线的 **DTW（动态时间规整）** 相似度 |
| KDJ 状态 | 20% | J 值位置、金叉状态、趋势方向 |

输出带**相似度百分比 + 分项得分 + 匹配的历史案例名**。
这是一个「**用历史牛股做模板，找当下相似的票**」的思路，我们完全没有。

**② 策略分类标记**：把结果分为「回落碗中 / 靠近多空线 / 靠近短期趋势线」，
比单纯给一个命中列表更有操作性。

**③ 自动过滤规则很细**：
- ST/*ST、退市、异常股
- **成交量为 0、收盘价异常、J 值均值超 80**
- **「最大量是阴量」直接剔除**（大资金出逃信号）——这条规则很有洞察力

**④ 钉钉推送 + K 线图**：选股结果自动生成 K 线图推送到钉钉群，含趋势线和成交量。
带**智能限流**（每分钟 20 条上限、最小间隔 2 秒、指数退避重试）。

**⑤ 智能更新判断**：3 点前不更新；3 点后检查每只是否有当天数据；100% 有则跳过。

### 1.3 局限

- **单策略**：只有碗口反弹一个策略 + B1 匹配，策略广度远不如我们（15 个）
- **CSV 存储**：全市场 6 年数据用 CSV，查询/扫描效率低于数据库
- **akshare 依赖**：数据源单一，akshare 限流时无降级
- **无回测**：只有选股，没有历史回测验证策略有效性
- **案例库需人工维护**：10 个案例是硬编码的，扩案例要改代码

## 二、项目 B：jin-ce-zhi-suan（金策智算）

### 2.1 是什么

**三个项目里最完整的**，定位是「智能投研决策系统」，
基于「三省六部」制度设计架构，支持回测、多策略管理、策略进化、LLM 选股。

**技术栈**：Python 3.8+ / FastAPI / DuckDB / 多数据源（AkShare/Tushare/JQData/Baostock/MySQL/PostgreSQL）
**许可证**：个人非商业免费 + 商业需授权（**非标准开源许可证**）

### 2.2 优点

**① 三省六部架构（分权协同 + 风控闭环）**

```
太子院 CrownPrince    数据前置校验与分发
中书省 ZhongshuSheng  策略信号生成
门下省 MenxiaSheng    风控审核（一票否决：止损/回撤/仓位约束）
尚书省 ShangshuSheng  执行调度与资金清算
─────────────────────────────────
吏部 策略注册与生命周期    户部 现金/成本/净值核算
礼部 业绩报表与策略排行    兵部 撮合执行与交易管理
刑部 违规记录与风险事件    工部 行情清洗与指标计算
```

**「门下省一票否决」** 是它的核心设计——策略信号必须先过风控才能执行。
我们已经有 `backtest.py` 借鉴了「尚书省批次持仓」，但**没有独立的风控层**。

**② LLM 自然语言选股**

用中文描述策略（如「五日内有涨停，涨停后缩量至一半以下，RSI 处于超卖区间」），
LLM 自动解析为「**结构化筛选条件 + 买卖执行规则**」两部分，可直接回测。

**③ 策略进化看板（Evolution）**

用 LLM 做策略的生成/评估/迭代——这是很前沿的方向。

**④ 多数据源工厂模式**

`DataFactory` 支持 AkShare / Tushare / JQData / Baostock / DuckDB / MySQL / PostgreSQL，
可切换。**DuckDB 做本地分析型存储**是个好选择（列式，聚合快）。

**⑤ 三层配置优先级**：环境变量 > `config.private.json` > `config.json`，
密钥不写进主配置。这个模式很规范。

**⑥ 依赖自检与自动安装**：启动时检查 `requirements.txt`，
缺失自动装，避免首次运行崩溃。

**⑦ SSE 进度推送**：后台自动选股刷新 + 全市场行情定时拉取 + SSE 实时进度。

### 2.3 局限

- **许可证非标准开源**：商业需书面授权，二次分发受限
- **架构偏重**：三省六部 10 个模块对一个中小项目可能过度设计
- **依赖较重**：LLM、多个数据源 SDK，部署复杂度高
- **LLM 依赖外部 API**：需要 Tushare token + LLM key 才能完整运行

### 2.4 与我们的关系（重要）

**我们已经在借鉴它了**：

```
server/backtest.py:2   借鉴 TSP 的「真实约束」思路 + 三省六部的「批次持仓」模型
server/backtest.py:13  批次持仓模型（借鉴 shangshu_sheng.py）
server/intent.py:3     借鉴三省六部框架 strategy_intent/human_intent_parser.py
server/tdx.py:3        借鉴三省六部框架 tdx/formula_compiler.py
```

而且我们在两个点上**做得比它更好**：

| 方面 | 三省六部原实现 | 我们的实现 |
|---|---|---|
| 通达信公式 | 拼成 Python 源码字符串 + `exec()` → **任意代码执行风险** | **白名单 AST 解释器**，拒绝未授权节点 |
| 自然语言解析 | 仅关键词包含判断 | 分词 → 多义词消解 → 结构化意图 → 策略映射 四步 |

## 三、项目 C：tradingview-mcp

### 3.1 是什么

一个 **MCP（Model Context Protocol）服务器**，把 TradingView 的数据能力
包装成 **37 个工具**开放给 AI（Claude/ChatGPT/Copilot/Cursor）。

**技术栈**：Python 3.10+ / uv / tradingview-ta / tradingview-screener / yfinance
**许可证**：MIT
**市场覆盖**：加密货币（KuCoin/Binance/Bybit/OKX）、美股（NASDAQ/NYSE）、土耳其 BIST、埃及 EGX

### 3.2 优点

**① 走查式回测（Walk-Forward）—— 最值得借鉴**

```
walk_forward_backtest_strategy
  → 训练/测试集切分
  → 过拟合判定：ROBUST / MODERATE / WEAK / OVERFITTED
  → 输出完整交易日志 + 净值曲线
```

**这是判断「策略是真的有效还是过拟合」的关键手段，我们完全没有。**
我们现在只能看「历史命中数」和「回测收益」，无法判断是否过拟合。

**② 9 个回测策略**（比早期 6 个增加 `rsi_pullback`/`keltner_breakout`/`triple_ema`），
且 `compare_strategies` 能横向排名全部 9 个。

**③ 多周期共振分析**

检查 **周线 / 日线 / 4 小时 / 1 小时 / 15 分钟** 五个周期的对齐情况。
我们只有日/周/月 K 线切换，**没有「多周期共振」的判定逻辑**。

**④ 技术指标深度**：30+ 指标，含**布林带智能评级系统**（-3 到 +3，
用于箱体挤压突破识别）、15 种 K 线形态检测。

**⑤ 情绪与新闻融合**

`market_sentiment` 抓 Reddit 金融社区返回看涨/看跌评分；
`financial_news` 拉 Yahoo/MarketWatch/CNBC；
`combined_analysis` 把**技术面 + 情绪面 + 新闻面**合成一个 BUY/SELL/HOLD 决策。

**⑥ 工程健壮性细节**（这些细节做得很好）：
- TradingView 限流处理：并发上限 4 + 最小间隔 0.8 秒，避免触发空响应
- Retry + 60 秒 TTL 缓存
- 用 rookiepy 自动读取浏览器 Cookie 获得实时数据（免 API Key）

**⑦ MCP 生态价值**：能直接接入 Claude Desktop / ChatGPT / Cursor，
**让 AI 助手直接调用**。这是「AI 原生」的接入方式。

### 3.3 局限

- **只服务海外市场**：美股/加密/土耳其/埃及，**没有 A 股**
- **无本地存储**：全部实时拉取，不落库，无法做长时间序列的自定义分析
- **无 Web 界面**：交互全靠 AI 对话
- **策略不可自定义**：9 个内置策略，不能写自己的
- **依赖 TradingView 可用性**：对方限流或改接口就受影响

```
                     run_strategies() 的 diag 新增 data_lag_days / data_note
server/app.py        /api/strategy_scan 透出这两个字段
```


### 5.2 待决策的升级项

按「价值 ÷ 成本」排序：

#### P0 · 走查回测（借鉴 tradingview-mcp）

**为什么优先**：这是唯一能回答「**我们的 15 个策略到底是真的有效，还是过拟合？**」的手段。
我们现在的回测只能看「这段历史赚了多少」，无法判断样本外表现。

**实现设计**：
```python
# server/backtest.py 新增
def walk_forward(rows, strategy_key, *, folds=5, train_ratio=0.7, **params):
    """滚动窗口：训练段调参 → 测试段验证，重复 folds 次。

    返回：
      segments: [{train_range, test_range, train_score, test_score}]
      verdict:  "ROBUST" | "MODERATE" | "WEAK" | "OVERFITTED"
      依据：测试段收益的均值/标准差、测试段与训练段的收益落差
    """
```

**难点**：
- **参数空间定义**：每个策略要暴露「可调参数」才能走查。现在 6 个历史策略的阈值
  是硬编码的（35%、±2%、0.85），需要先参数化 → 这是一次波及 `screener.py` 的改动
- **判定标准需要标定**：ROBUST/MODERATE/WEAK/OVERFITTED 的阈值不能拍脑袋，
  要用我们的历史数据实测出一批样例来定
- **计算量**：5 folds × N 组参数 × 全市场，需要考虑耗时

**建议**：先只对**单个策略 + 小参数网格**做，验证方法论可行后再扩。

#### P1 · 形态相似度匹配（借鉴 a-share-quant-selector）

**思路**：建「成功案例库」→ 提取特征 → DTW 匹配当下相似的股票。

**难点**：
- **案例库从哪来**：a-share-quant-selector 是人工挑 10 个案例。我们需要一个
  **可自动生成的案例标准**——例如「某策略命中后 N 日涨幅 > X%」的票作为正样本。
  这需要先有走查回测的结论支撑（否则不知道什么算"成功"）
- **DTW 计算成本**：DTW 是 O(n²)，全市场 5565 只 × 案例库 N 个，需要优化
  （可用 FastDTW 或先做粗筛）
- **四维权重需要标定**：30/25/25/20 是它的经验值，我们要用自己的数据验证

**依赖**：建议在 P0 走查回测之后做（先知道什么有效，再定义"成功案例"）。

#### P2 · 策略池扩展到北交所（补齐短板 #7）

**为什么做**：历史库已有 344 只北交所数据（价值实证：`bj920427` 库里 250 行
vs 腾讯源仅 1 行），但策略扫不到——数据白买了。

**实现**：
```python
# server/datasource.py
def pool_rows(pool="all", max_workers=8, scope="snapshot"):
    """scope="snapshot"（默认，3761 只）
       scope="all"     （eltdx 全量代码表，5565 只，含北交所）"""
```

**难点**：
- 北交所股票的正股 PE/PB/市值等字段可能缺失，策略需能容忍 None
- `_limit_pct` 已有 `bj → 30%` 判定，这个没问题
- 行情快照要能覆盖北交所（现在的 `quote_tencent` 是否支持需验证）

#### P3 · 定时同步（借鉴 a-share-quant-selector 的智能更新）

```bash
# 收盘后自动同步 + 刷新历史引擎缓存
5 15 * * 1-5 cd /workspace/tick-stock-panel && .venv/bin/python -u scripts/sync_bars.py --scope all
```
同步完成后调 `history.reload_engine()`。

#### 明确不建议做的

| 项 | 理由 |
|---|---|
| **LLM 自然语言选股** | 你本次选择「暂不做 LLM」。且我们已有 `intent.py` 覆盖基本需求 |
| **多数据源工厂** | 我们已有腾讯+新浪+eltdx 降级链，够用。加 tushare/jqdata 需要付费 token |
| **换 DuckDB** | 现在 SQLite 500MB 表现良好，历史引擎 3.3 秒加载完全够用 |
| **MCP 化** | 定位不同。我们是 Web 面板，不是给 AI 用的工具服务器 |
| **三省六部完整架构** | 对当前规模过度设计，且已借鉴其核心（批次持仓/意图解析/公式编译） |
| **钉钉推送** | 低优先级，且需要用户配置 webhook |
