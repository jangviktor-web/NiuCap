# 走查回测（Walk-Forward）说明

> 借鉴 [atilaahmettaner/tradingview-mcp](https://github.com/atilaahmettaner/tradingview-mcp)
> 的 `walk_forward_backtest_strategy`，用于回答一个现有回测答不了的问题：
> **「策略的参数是真有效，还是拟合了历史噪声？」**
>
> 实现文件：`server/walkforward.py`
> API：`GET /api/walk_forward`
> 落地时间：2026-09-22

---

## 一、它解决什么问题

现有回测（`backtest.py`）只能回答「这段历史赚了多少」。但一个策略在某段历史
上表现好，可能只是**过拟合**——参数恰好拟合了那段历史的噪声，换一段就失效。

走查回测的做法：

```
把历史切成 N 折，每折里：
  训练段（前 70%）→ 在这段上挑收益最好的参数
  测试段（后 30%）→ 用挑出的参数，在从未见过的数据上验证
汇总 N 折的测试段表现 → 判定策略稳健还是过拟合
```

核心价值：**训练段好不算数，测试段好才算数。**

---

## 二、判定标准

| 判定 | 条件 | 含义 |
|---|---|---|
| **ROBUST** | 测试段均值 > 0 且 ≥60% 折为正 且 衰减 < 40% | 参数稳健 |
| **MODERATE** | 测试段均值 > 0 且 ≥40% 折为正 | 可用，需控制仓位 |
| **WEAK** | 测试段均值 > 0 但少数折为正 | 依赖特定行情 |
| **OVERFITTED** | 测试段均值 ≤ 0 | 样本外失效 |
| **INSUFFICIENT** | 凑不出完整闭环的折 | 数据/信号不足，**不下结论** |

**额外规则**：有效折 < 2 时，即使命中 ROBUST 条件也强制降级为 WEAK——
「1 折全对」是运气，不是稳健。

**为什么 `decay` 用绝对差而不是百分比**：
最初写的是 `(train - test) / |train|`，但训练均值接近 0 时分母趋零，
实测会输出 `-1730%`、`8455%` 这类无意义的数字。改成 `train - test`（绝对差）
后数值稳定。使用时**必须配合 `train_avg` 一起看**——单看 decay 会误判量级。

## 三、与线上策略的一致性保证

走查不能自己另写一套判定逻辑，否则结论无法代表线上策略。为此做了两层验证：

**① 指标层**：走查的 `_metrics_at()` 与 `history.HistoryEngine.metrics()`
在 120 只股票 × 10 个指标 = **1040 项比对中 0 处不一致**。

过程中发现一个口径陷阱并已修正：

```python
# history.py 里三个指标的「含不含当日」口径不同：
m["hhv20"]       = _hhv(H[:-1], 20)      # 不含当日
m["range60_pct"] = _range_pct(H[:-1], L[:-1], 60)   # 不含当日
m["chg20"]       = _chg_pct(C, 20)       # ← 含当日！
```

`_chg_pct(close, period)` 的定义是「`close[-1]` / `close[-(period+1)]` - 1」，
**内部已经含当日**。最初误传 `C[:-1]`，等于多排除一天，导致北交所股票
`chg20` 全部对不上（52/520 不一致）。修正后归零。

**② 参数层**：策略参数化改造后，不传参数时的命中名单与改造前
**逐只完全一致**（6 个历史策略、同一份固化快照、集合相等）。

## 四、实测结果与重要限制

### 4.1 ✅ 关键改进：历史窗口已从 1 年扩到 2 年

最初实测发现数据只有 267 根（约 1 年），走查有效性很差。
**追查后发现这是引擎的读取窗口限制，不是数据源的限制**：

```python
# server/history.py
LOOKBACK_DAYS = 760        # 原为 400（约 1 年）→ 现 760（约 2 年）
```

库里的数据其实存到了 **2024-08-29**，只是 `LOOKBACK_DAYS=400` 把它截断了。
实测三档：

| LOOKBACK_DAYS | 覆盖 | 行数 | 每只根数 | 加载耗时 |
|---|---|---|---|---|
| 400（旧） | 1.1 年 | 145 万 | **267** | 5.8s |
| **760（现）** | 2.1 年 | 270 万 | **500** | **9.6s** |
| 1200 | 3.3 年 | 271 万 | 500 | 9.6s（已到底，无收益） |

取 760 是「**榨干现有数据**」的最优点：多付约 4 秒加载时间，换来 87% 的额外样本量。
再往上加没有收益（库里最早的日线就是 2024-08-29）。

### 4.2 改进效果（150 只随机抽样，3 折走查）

| 策略 | 稳健+中等占比（1年 → 2年） | 有效折中位数 |
|---|---|---|
| `pullback_ma20`（回踩企稳） | 4.7% → **41.3%** | 1 → 2 |
| `breakout_20h`（突破新高） | 4.7% → **21.3%** | 1 → **3** |
| `ma_bull`（均线多头） | 2.7% → **21.3%** | 1 → 2 |
| `volume_surge`（放量突破） | 7.3% → **18.7%** | 2 |
| `oversold_rebound`（超跌反弹） | 2.0% → 6.7% | 1 |
| `platform_break`（平台突破） | 0% → 0.7% | 1（仍稀疏） |

**改进前**（267 根）的完整分布：

```
策略                 稳健  中等   弱  过拟合   不足 | 稳健+中等
volume_surge          4    7   14    67    58 |  7.3%
breakout_20h          1    6   18    95    30 |  4.7%
pullback_ma20         6    1   25    59    59 |  4.7%
ma_bull               2    2   14    58    74 |  2.7%
oversold_rebound      1    2   19    35    93 |  2.0%
platform_break        0    0    3     4   143 |  0.0%
```

**改进后**（500 根）：

```
策略                 稳健  中等   弱  过拟合   不足 | 稳健+中等
pullback_ma20        36   26   20    51    17 | 41.3%
breakout_20h         20   12    8   110     0 | 21.3%
ma_bull              16   16   17    89    12 | 21.3%
volume_surge         16   12   21    91    10 | 18.7%
oversold_rebound      5    5   56    16    68 |  6.7%
platform_break        1    0   12    24   113 |  0.7%
```

### 4.3 怎么读这张表

**分布本身是合理的**，这反过来证明工具没有失灵：

- `pullback_ma20` 排第一（41.3%）。它逻辑最清晰（趋势中回踩+缩量），
  参数只有 2 个、网格 9 组，信号密集 → 统计最可信。
- `platform_break` 仍然垫底（0.7%，113/150 不足）。它要求「前 60 日振幅 ≤35%
  + 放量突破」，天然极稀疏，很多标的根本凑不出足够信号。
  **0.7% 要读作「测不出来」而不是「策略差」。**
- 如果代码有 bug 导致永远输出 ROBUST，不会有这种梯度。

**仍需注意**：500 根做 3 折，每折可用约 147 根，训练段约 103 根——
比之前好得多，但对 MA60 预热来说仍偏紧。稳健率 20~40% 是**合理但不惊艳**的水平，
符合「公开的简单技术策略在样本外多半会衰减」这一常识。

### 4.4 后续可做的（按性价比）

| 优先级 | 动作 | 说明 |
|---|---|---|
| ~~P0~~ | ~~扩充历史数据深度~~ | ✅ **已完成**（400 → 760 天，见 4.1） |
| **P0** | **同步更长历史** | 库里止于 2024-08-29。`scripts/sync_bars.py --count 1200` 可拉约 5 年，走查可靠性会再上一个台阶 |
| P1 | 跨标的批量走查 API | 单标的有效折仍偏少；按策略聚合 100+ 只才有统计意义（当前是脚本实现，未开 API） |

### 4.5 折数的选择（实测对照，基于改进前的 267 根）

| 配置 | 有效折中位数 | 可评估标的数(共80) |
|---|---|---|
| folds=5, min=3 | 1 | 59 |
| folds=3, min=3 | 1 | 59 |
| **folds=3, min=2** | **2** | **62** ← 采用为默认 |
| folds=3, min=1 | 2 | 68 |
| folds=2, min=2 | 1 | 60 |

`min_signals` 降到 2 能让更多标的进入可评估状态。降到 1 会进一步扩大样本，
但「1 次信号就选参数」噪声太大，不采用。**自适应门槛**（`adaptive_min=True`）
会在策略天然稀疏时自动下调，避免像 `platform_break` 那样每折都被跳过。

> 数据扩到 500 根后，`folds=3` 的有效折中位数已升到 2~3。
> 若未来数据再扩到 1000 根，可考虑把 `folds` 提到 5。

## 五、API 用法

```bash
# 单标的走查
curl 'http://127.0.0.1:8899/api/walk_forward?code=sh600519&strategy=breakout_20h'

# 调折数 / 观察期
curl 'http://127.0.0.1:8899/api/walk_forward?code=sz000001&strategy=pullback_ma20&folds=5&horizon=10'
```

返回结构：

```json
{
  "code": "sh600519",
  "strategy": "breakout_20h",
  "strategy_name": "突破新高",
  "bars": 267,
  "date_range": ["2025-08-18", "2026-09-21"],
  "verdict": "WEAK",
  "detail": "仅 1 折有效，样本太少不足以判定稳健；……",
  "sparse": true,
  "folds": [
    {"fold": 1, "best_params": {"hold_ratio": 0.95},
     "train": {"n_signals": 2, "avg_ret": -0.7066, "win_rate": 0.0},
     "test":  {"n_signals": 3, "avg_ret": 1.5881,  "win_rate": 66.7}},
    {"fold": 2, "skipped": true, "reason": "训练段信号不足 2 次，参数不可信"}
  ],
  "summary": {
    "n_folds_valid": 1, "n_folds_no_test_signal": 1, "n_folds_skipped": 1,
    "train_avg": -0.7066, "test_avg": 1.5881, "test_std": 0.0,
    "decay": -2.2947, "test_positive_rate": 100.0,
    "horizon": 5, "grid_size": 3, "min_signals_used": 2
  }
}
```

`summary` 里三个计数字段的含义要分清：

| 字段 | 含义 |
|---|---|
| `n_folds_valid` | 训练选出了参数 **且** 测试段有信号 → 真正验证到的折 |
| `n_folds_no_test_signal` | 选出参数了，但测试段没信号 → **没测到**（不是"表现差"） |
| `n_folds_skipped` | 训练段信号就不够，参数本身不可信 |

把 `no_test_signal` 算进"正折比例"会让结论失真，所以代码里显式排除。

## 七、数据深度的实测证据

**改进前**（`LOOKBACK_DAYS=400`）的长度分布——注意 `p75 = max = 267`：

```
总股票数: 5565
序列长度: min=3  p25=267  中位=267  p75=267  max=267
长度 >= 200 的股票: 5431 只 (97.6%)
长度 >= 300 的股票:    0 只 ( 0.0%)   ← 断崖
```

`p75 = max` 这种「整齐的截断」是**人为窗口**的典型特征，不是数据源的限制。
顺着这条线索查库就发现：`daily_bars` 里最早的数据是 **2024-08-29**，
即库里有 500 根，是引擎把读取窗口设成了 400 天。

**改进后**（`LOOKBACK_DAYS=760`）：

```
引擎: {'codes': 5565, 'as_of': '2026-09-21', 'rows': 2705080}
序列长度: 中位=500  p75=500  max=500
```

> **教训**：看到「所有序列长度都相等」时，先怀疑是人设置了窗口，
> 而不是数据天然如此。差一点就把「读取窗口太窄」误判成「数据源只有 1 年」，
> 进而得出「策略无法验证」的错误结论。

## 八、已知的坑（写代码时会踩到）

1. **`lookback` 不要硬编码成 600**。历史长度受 `LOOKBACK_DAYS` 控制，
   传超过库中实际根数的值会被静默截断，看起来"用了更多数据"其实没有。
   默认 `lookback=0`（用全部可用），这是安全的选择。

2. **`_chg_pct` 的「含当日」口径**。`history.py` 里 `hhv/llv/range` 传
   `arr[:-1]`（不含当日），但 `chg20` 传完整数组（含当日）。
   走查里混用会导致 `chg20` 系统性偏移（实测北交所股票全部对不上）。

3. **测试段 0 信号 ≠ 测试段表现差**。前者是「没测到」，必须从分母里排除，
   否则「正折比例」会被稀释成假象。代码用 `n_folds_no_test_signal` 单独计数。

4. **`decay` 用绝对差**。用百分比会在训练均值趋零时爆炸（实测出现 8455%）。
   必须配合 `train_avg` 一起读。

5. **有效折 < 2 时强制降级为 WEAK**。「1 折全对」是运气，不是稳健。
